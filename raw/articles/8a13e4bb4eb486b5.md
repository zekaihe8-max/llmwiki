# 203 页「Little Book of Agent Engineering」用 11 章讲透模型之外的 Harness Engineering

15 min read

一个 Agent 能修好示例里的 Bug，不代表它能稳定处理真实仓库。它可能第 2 次就找错文件，第 10 次开始反复调用同一个工具，任务更长时又忘了最初的约束。

读完 [@__paleologo](https://x.com/__paleologo) Gappy + Agents 的「The Little Book of Agent Engineering」，这本 203 页的小书，把这些看似分散的问题放进同一个工程框架：模型负责选择下一步，外围程序负责提供信息、限制行动、执行操作、保存状态，以及判断任务是否真的完成。

书中用 harness 指代这套模型之外的运行与控制系统。对于大多数直接使用现成模型的研发团队，这恰好是自己最能改进的部分。

全书 11 章覆盖了模型接口、Agent 循环、工具、上下文、检索与记忆、长任务、多 Agent、安全和评估，既有工程原理与已有研究梳理，也配套了一个约 400 行 Python 的教学实现 miniagent。

我认为它最值得讨论的问题是：当底层模型已经确定，我们还能通过哪些系统设计，让 Agent 更可靠、更便宜，也更可控？

### 1. Agent 工程的起点：模型提出行动，程序决定行动能否发生

书中对 Agent 的定义很具体：模型反复选择行动，程序执行行动，将观察结果交回模型，直到模型结束任务或预算耗尽。

按照这个定义，调用 1 次模型不算 Agent。预先固定好步骤的调用链属于工作流。两者的关键差异，是下一步由谁决定。

一个完整的 Agent 循环包含这些部分：

组件

负责什么

典型工程问题

模型 π

根据当前上下文选择行动

选哪个模型，用多少推理预算？

循环

安排行动、处理观察、结束运行

如何处理截断、超时、预算耗尽？

工具与环境

提供可执行操作及其反馈

返回哪些信息，允许哪些副作用？

上下文构建器 φ

决定这一轮让模型看到什么

保留、删除、检索哪些材料？

外部存储 M

保存日志、文件、记忆与进度

如何找回信息，如何更新过期内容？

权限检查 g

允许、询问或拒绝行动

哪些操作必须审批？

评估器 R

检查最终结果

Agent 说完成了，环境里真的完成了吗？

用最简形式表达，就是先构建上下文 cₜ = φ(hₜ, M)，模型再从行动分布 π(·|cₜ) 中提出下一步。只有通过权限检查，工具才会执行。

[/shao__meng/article/2125124722216276171/media/2125120037250125824](/shao__meng/article/2125124722216276171/media/2125120037250125824)

这里有一个容易被产品演示掩盖的事实：模型本身没有执行工具。它生成的是一个调用请求。验证参数、检查权限、实际运行，以及返回结果，都由外围程序完成。

因此，修复 Agent 的失败，不能只想到换模型、改提示词。找不到文件，可能是搜索接口有问题；找到后没读懂，可能是工具输出被截断；明明没成功却宣布完成，可能是结束条件和验证机制有缺口。

### 2. 先决定要多少自主性，再讨论用什么框架

书中给出的架构顺序是：普通程序、工作流、路由器、Agent、多 Agent。

越往后，模型决定的控制流程越多。灵活性随之增加，可预测性、调试便利和成本控制通常会变差。实际产品往往混用这些结构，例如一个固定工作流中的某一步，由一个小型 Agent 自主完成。

判断是否值得使用 Agent，可以先回答 4 个问题：

- 执行路径是否无法提前写死？
- 结果能否通过环境反馈验证？
- 错误是否便宜、可恢复？
- 任务价值是否足以覆盖延迟和推理成本？

代码修复适合 Agent，原因也在这里。定位过程经常需要临场判断；测试能提供反馈；工作副本可以回滚；修复真实问题通常值得消耗若干轮调用。

反过来，每晚将固定 CSV 转成固定版式 PDF，普通程序就够了。将客服邮件分到 5 个队列，路由器可能已经足够。让模型每一步都重新决定，会平白增加不确定性。

书中对 Agentless 和 SWE-agent 的讨论也说明，同一个任务可以采用不同架构。前者将定位、候选补丁和测试组织成固定流程，后者允许模型逐步探索。具体哪一种更好，要结合任务覆盖率、成本和可调试性衡量。

对研发团队来说，值得坚持的原则是：选择能够解决问题的最低自主程度，并为额外的自主性提供收益证据。

### 3. 长任务为什么容易失败：关键在于发现并修复错误

书中用一个简单计算解释长任务的困难。

假设每一步正确的概率为 r，各步独立，而且任意一次错误都会导致任务失败。完成 T 步的成功率就是 r^T。

条件

整体成功率

单步正确率 99%，连续 100 步

约 36.6%

单步正确率 95%，连续 50 步

约 7.7%

单步正确率 95%，50 步，90% 的错误可被发现并修复

约 77.8%

第三行引入了检测概率 d。如果被发现的错误都能修复，那么每一步真正致命的概率，就从 1-r 降为 (1-r)(1-d)，整体成功率近似为 [1-(1-r)(1-d)]^T。

这是理想化计算。现实中的错误会相关，修复会消耗预算，验证器也可能漏检或误判。77.8% 不能直接视为真实 Agent 的实验成绩。

[/shao__meng/article/2125124722216276171/media/2125120417996406784](/shao__meng/article/2125124722216276171/media/2125120417996406784)

但这个例子清楚说明了为什么验证工具如此重要。提高模型单步能力是一条路径，提高错误发现率、让修复成为可能，也能显著改变长任务表现。

书中将验证信号大致排列为：确定性的类型与格式检查、可执行测试和明确答案、带评分标准的模型评审，以及缺少新证据的自我反思。

每一种方法都有范围限制。类型检查不能证明业务正确，测试受覆盖率约束，模型评审需要人工样本校准。单纯再问一句“你确定吗”，没有给系统增加新的证据，改错也可能变成改坏。

因此，任务要求应尽可能写成可检查的完成条件。例如“修复 test_stats.py 暴露的问题，且不得修改测试”，比“把代码处理好”更适合进入可靠的执行循环。

### 4. 工具接口直接影响模型表现，错误信息尤其重要

贯穿全书的案例，是修复 trailing_mean(xs, w)。它应当返回每个位置向后看的滑动均值，但实现错误地向前取窗口。

输入 [10,20,30,40]，窗口为 2，正确结果应为 [10,15,25,35]。错误实现返回 [15,25,35,40]。

教学示例的执行顺序是：先运行测试，读取带行号的源码，将 xs[i:i+w] 改为 xs[max(0,i-w+1):i+1]，再运行测试，最后解释修复内容。

这段轨迹有意使用脚本模型重放。它用于检查执行系统是否按预期工作，不能证明真实模型会做出同样的选择。

更值得复用的是工具设计：

- 文件读取返回行号，方便引用和定位。
- 搜索返回 file:line: text，命中结果可以直接打开。
- 测试输出以 PASSED 或 FAILED 开头，减少被长日志掩盖的风险。
- 编辑工具要求旧字符串只出现 1 次，否则拒绝修改，并提示增加定位上下文。
- 大输出支持分页、筛选，发生截断时明确告知。

“找到 3 处匹配，请提供更多上下文”是一条有用的观察。静默修改第 1 处匹配，则可能让错误以成功状态继续传播。

工具粒度也需要权衡。通用 Shell 很灵活，但权限系统面对的是一段自由文本命令。专用的 restart_service(name) 或 edit_file(path, old, new)，更容易做参数验证、范围限制和审计。

MCP 解决工具的发现和调用协议，Skills 则将操作流程按需加载。前者不自动提供授权，后者也不需要将全部说明常驻上下文。工具越多，越需要区分“系统接入了什么”和“这一轮应向模型暴露什么”。

### 5. 上下文管理首先是一项信息选择工作

模型每一步能使用的信息，取决于当前请求提供了什么。系统保存着完整日志，不代表模型这一轮看到了完整日志；模型曾经读过一个文件，也不代表文件仍然存在于当前上下文中。

书中把上下文视为一个有限预算：系统说明、工具定义、历史、检索材料，以及预留输出空间，共同占用窗口。

窗口变大，并不意味着应该尽量填满。无关文件会造成干扰，修改前的测试日志会变成过期证据。书中引用 Lost in the Middle、RULER 和 Context Rot，讨论标称窗口与实际使用信息能力之间的差距。

它还引用了编码和数学 Agent 的一项研究：原始上下文中，工具观察约占 84%，推理约占 10%，行动约占 6%。这个比例对应特定研究任务，不能推广为所有 Agent 的固定构成，但它提示了优先优化的对象：先检查大量工具输出，再考虑压缩每一句提示词。

书中将缩减上下文的方法分为 4 类：

方法

具体做法

信息如何找回

Bound

工具从源头分页、筛选、限制返回量

需要时请求更精确的内容

Elide

将较旧的长结果换成简短占位说明

从记录或重新调用中获取

Offload

将中间结果、计划和笔记写入文件

保留路径，按需读取

Compact

用摘要替换长历史，继续执行

摘要遗漏的信息不再直接可见

[/shao__meng/article/2125124722216276171/media/2125120500968169472](/shao__meng/article/2125124722216276171/media/2125120500968169472)

前几种方式保留了取回材料的路径，应优先考虑。摘要压缩则需要明确保护任务目标、权限限制、完成条件、已经失败的尝试和下一步。

这里还有一个工程细节：重新运行工具，未必能取回原来的观察。外部页面会变，代码会被修改。对需要精确追溯的内容，保留原始结果与版本比“到时再读一遍”更稳妥。

上下文成本也值得计算。假设固定提示与工具定义占 c₀ tokens，每一步新增 Δ tokens，并在之后持续携带。按书中的近似计数，T 步累计输入为 Tc₀ + ΔT(T+1)/2。

当 c₀=5,000、Δ=2,000、T=50 时，累计输入约为 280 万 tokens。这个数字描述未压缩历史下的逻辑输入量，实际账单还取决于缓存价格和命中情况。

因此，稳定的前缀和只追加的历史很有价值。每一步改写系统提示中的时间戳，或随意调整工具顺序，都可能破坏后续缓存。另一方面，频繁删改旧结果也会影响缓存，批量压缩往往比每一步都重新整理更值得测试。

### 6. 检索负责读，记忆负责写，两条路径应分开评估

在书中的框架里，外部存储有两条路径：检索将材料送入上下文，记忆决定为未来保存什么。

固定 RAG 在生成前检索一次，适合边界清楚的查询。Agentic retrieval 将搜索和打开文档做成工具，模型可以调整查询、沿引用追踪，适合答案需要多步探索的问题，代价是更多调用和更复杂的停止条件。

搜索方法也应该匹配材料：精确函数名、异常文本适合关键词搜索；语义改写适合向量搜索；混合搜索可以通过倒数排名融合（RRF）合并排序，再用重排模型筛选少量候选。

RAPTOR 和 GraphRAG 处理的是另一种问题：答案分布在整份文档或多份文档中，单个文本块无法承担总结。层次摘要和图结构可以帮助聚合，但索引构建会增加模型调用。应当先通过评估发现此类失败，再引入更复杂的索引。

书中提醒，最终回答错误至少可能发生在 3 个位置：材料没检索到；材料已出现但被误读或忽略；一次错误检索改变了后续探索方向。

所以，召回率 recall@k、平均倒数排名（MRR）和最终答案质量不能混为一谈。引用检查也至少有两层：引用的文档是否真的读过，以及文档是否支持对应的具体判断。

权限过滤应发生在检索阶段。已经将越权材料交给模型，再要求它不要泄露，边界就放错了位置。

记忆同样需要来源、版本和更新机制。偏好、项目事实、失败经验和操作流程的有效期不同。书中借用工作记忆、情景记忆、语义记忆和程序记忆区分这些内容，但分类本身不能保证记忆有效。

对工程团队，更实用的问题是：未来是否真的需要这条信息，能否从原始材料重新获得，冲突时如何更新，恶意文档中的要求是否被误存成长期规则。一个可以搜索的文件，有时已经比专门的记忆系统更合适。

### 7. 长时间运行需要进度交接，也需要处理副作用的不确定状态

Agent 跨越多个上下文窗口后，需要一套让后继会话继续工作的机制。

书中借鉴长运行编码 Agent 的做法：初始化阶段建立环境、目标清单和启动脚本。后续会话读取进度记录与版本历史，验证继承状态，再完成一个有边界的目标，留下可核查的进展。

这里最重要的是，目标只有通过验证才能标记完成。进度文件里的“已完成”，如果仍然只来自模型的判断，就没有比对话中的承诺更可靠。

程序崩溃和网络超时还会引入另一种问题：请求发出去了，但没有收到确认，操作到底有没有发生？

对于读取，重试通常容易处理。对于发送邮件、发布报告或付款，盲目重试可能重复执行。书中建议在执行前记录 pending 状态，并使用目标服务认可的幂等键。重试应复用同一逻辑操作的键；服务不支持幂等时，就查询目标状态进行核对。

丢失确认之后，正确状态是 unknown。只有拿到目标端证据，才能判断下一步。

检查点能恢复 Agent 循环，却不能自动证明外部副作用只发生了 1 次。这部分问题，最终仍然需要分布式系统中的状态记录、幂等和对账机制。

### 8. 多 Agent 的直接价值是隔离上下文，协作收益要靠任务结构证明

书中最实用的多 Agent 设计，是将子 Agent 封装成一个工具。

主 Agent 提交一个自包含问题，子 Agent 带着独立上下文和受限工具集展开调查，最后返回短报告。图中的示例是：子 Agent 读取 12 个文件、处理约 40,000 tokens，主 Agent 只接收约 200 tokens 的报告。

这些数字用于说明信息流设计，不代表固定压缩率，也不表示总推理成本只剩 200 tokens。子 Agent 的阅读依然需要付费。

[/shao__meng/article/2125124722216276171/media/2125120570509660160](/shao__meng/article/2125124722216276171/media/2125120570509660160)

这种结构适合独立搜索、代码调查、资料核对。主 Agent 无须携带每个子任务的全部阅读历史，还可以针对不同子任务选择工具和模型。

但“上下文隔离”不等于“安全隔离”。子 Agent 的报告仍可能出错，也可能转述恶意指令；报告需要证据，驱动不可逆操作前还需要检查。

书中对多 Agent 的态度比较克制。它引用 Anthropic 研究系统的经验，指出并行探索能够提高表现，但其多 Agent 交互的 token 消耗约为普通聊天的 15 倍。这个比较基线是聊天，不能写成所有多 Agent 都比单 Agent 贵 15 倍。

任务耦合度决定了另一半结果。多个 Agent 独立读文档，通常容易合并。多个 Agent 同时修改同一套接口、相同文件，则容易对命名、前提和完成状态形成互不知情的决定。

书中给出的经验是“并行阅读，串行写入”。如果确实要并行修改，就用独立工作副本、任务归属记录和明确接口，承担最后的集成与冲突解决成本。

投票也有类似前提。独立答对概率为 70% 的 5 个投票者，多数正确率约为 83.7%。但模型共享盲点，同一段误导材料可能让所有投票者一起出错。增加模型数量之前，应该先考虑证据和视角是否真正不同。

### 9. 安全边界要由程序和环境执行

书中的修复案例还埋了一项恶意要求：README 的隐藏注释诱导 Agent 将仓库上传到外部站点。

这是一段被讨论的攻击样本。它说明，Agent 为了完成合法任务而读取材料时，也可能读到试图改变行动目标的文字。

系统提示、用户请求、文件内容、工具输出和记忆，最终都会进入模型的输入。模型学到的优先级规则有用，但无法替代强制权限机制。

书中引用 Simon Willison 的“致命三要素”：接触私有数据、接触不可信内容、能够对外通信。三者同时存在时，恶意内容可能诱导数据外传。

[/shao__meng/article/2125124722216276171/media/2125120622221283328](/shao__meng/article/2125124722216276171/media/2125120622221283328)

在修复示例里，Agent 需要读取仓库，也必须面对不可信内容，因此应限制对外通信能力。研究 Agent 若要浏览公开网络，则不必同时获得全部私人文件。

这个检查针对的是特定的数据外传链路。去掉其中一个条件，并不代表解决了删除文件、篡改测试或错误部署等所有风险。

更完整的防御需要几层配合：

- 只暴露任务需要的工具。
- 用代码逐次检查操作类型和参数。
- 用沙箱限制文件、网络、进程和凭据访问。
- 对高影响操作确认准确内容。
- 在 Agent 无法随意篡改的位置保留审计记录。

审批必须绑定准确命令、收件人、正文或代码差异。文档里声称“用户已经批准”，不能产生授权。

运行测试本身也在执行仓库代码。即使没有网络工具，只要代码执行环境仍能自由访问网络，外传路径就可能继续存在。工具层限制和运行环境隔离需要同时考虑。

书中还介绍了先规划后执行、双模型，以及 CaMeL 的数据来源跟踪。它们尝试限制不可信材料影响控制流程，或约束敏感数据能够流向哪里。这些设计会牺牲部分灵活性，适合根据风险等级选择。

### 10. “3 次里成功 1 次”和“连续成功 3 次”，是两种完全不同的产品

Agent 的评估对象应是最终状态：代码是否通过独立测试，数据库是否出现正确记录，文件是否满足约束。模型声称自己做过什么，只能辅助诊断。

每次试验还应从干净环境开始。更严格的做法是，将 Agent 产生的文件或差异复制到另一个全新环境，再运行验证器，避免残留进程或被修改的测试运行器影响评分。

指标选择同样会改变我们对能力的理解。假设某个任务单次成功概率为 70%，并暂按各次尝试独立计算：

指标

回答的问题

k=3 时

pass@k

最多尝试 k 次，至少 1 次成功的概率

97.3%

pass^k

k 次全部成功的概率

34.3%

[/shao__meng/article/2125124722216276171/media/2125120678189989888](/shao__meng/article/2125124722216276171/media/2125120678189989888)

前者适合有可靠验证器、能够从多个候选中挑选成功结果的场景。后者反映重复执行的一致性。如果产品只提交 1 个结果，单次成功率依然需要单独报告。

这也解释了为什么一次精彩演示无法证明系统可靠。候选生成与持续自动执行，对失败的容忍方式不同。

评估集规模决定能判断多小的提升。书中用近似计算说明，在成功率约 70% 的非配对二元比较里，想让 5 个百分点的差异达到约 2 个标准误，需要约 670 个任务。这个数量级估算并非完整的统计功效设计，却足以提醒团队：几十个样本通常只能识别较大的变化。

实践上，可以先从 20 至 50 个真实任务起步，包含已经发生的失败、常规回归、攻击样本和无关干扰。这个规模适合启动迭代，不能支撑所有小幅领先的结论。

比较两个版本时，应尽量使用相同任务做配对分析，记录不确定性，同时报告成本、延迟、步骤数、工具错误和审批次数。

验证器也需要测试。参考解应该能够通过，已知作弊方式应该被拒绝，真实需求与评分检查要一一对应。模型评分器还需要人工标注样本校准，避免偏好长答案或特定表达风格。

### 11. 把全书落成研发流程：每次失败都要指向一个可修改的组件

这本书最后回到一个朴素的迭代流程：运行真实任务，收集轨迹，归类失败，形成假设，修改一个组件，再与基线比较。

如果把它用于当前的 Agent 项目，我会优先做这些工作：

- 写清可验证的完成条件，区分 answered、budget_exhausted、stopped 与真正成功。
- 检查工具错误是否足够具体，大输出是否能分页和重新定位。
- 查看任务第 1 步与第 50 步的上下文，确认目标、约束和当前证据仍然可见。
- 为长任务保留可核对的进度，为外部副作用记录执行状态。
- 以强单 Agent 为基线，只在独立探索有收益时加入子 Agent。
- 将模型、提示、工具、上下文策略、权限策略和运行代码一起版本化。
- 保留失败轨迹，将生产中的新问题转成回归任务。

这里的局限也要明确。教学用 miniagent 便于理解核心循环，离生产系统还隔着真正的隔离环境、可靠持久化、复杂授权和运维。全书引用不同年代、不同模型与任务的研究，局部收益不能直接当作当前产品的收益承诺。示例中的模型标识符、API 和协议版本，也应以实际采用服务的文档为准。

这不妨碍它提供一套稳定的分析方法：失败发生后，先分清是系统机制、输入材料，还是评估本身出了问题。
