LangChain 谈主动式 Agent：超七成运行靠日程，关键是记忆与人的注意力

[@LangChain](/LangChain) 团队 [@sydneyrunkle](/sydneyrunkle) 总结了团队构建主动式 Agent 的经验：当 Agent 开始在后台推进持续数天、数周的目标，瓶颈不再只是模型能不能完成任务，而转为人有没有时间处理它不断送来的问题和结果。

以内部的销售 Agent 和工程 Agent Robin 为例，提出两个核心：用记忆提高判断质量，用交互设计减少人的评审负担。

# 主动不是不断发消息，是不必每次等指令

主动式 Agent 有三类触发来源：现实事件，例如新邮件、新 PR；开发者设定的日程，例如夜间整理记忆、每周清理陈旧 PR；以及 Agent 根据任务自行创建的日程，例如第二天跟进，或按用户要求建立每日简报。

LangChain 的 GTM Agent 负责跟进销售线索、处理回复和起草邮件；Robin 的前身是 Open SWE，负责起草和审查 PR。两者都基于 Managed Deep Agents 构建。团队介绍，超过 70% 的运行由日程触发，而不是人临时输入提示。

这个数字反映的变化是：Agent 不再只围绕一轮对话工作，而是通过事件和日程持续推进已有目标。

# 记忆不只是记录历史，更要帮助判断什么值得处理

Agent 被事件或日程唤醒时，往往没有新的人工说明。连接器可以提供最新邮件和项目状态，但用户的偏好、此前的纠正和合作习惯，需要从记忆中获得。

记忆来源分成三类：已有资料，例如过去发送的邮件；当下反馈，例如草稿被修改或拒绝的原因；行动结果，例如发出的邮件是否收到回复。

难点不在写文件，而在持续维护：哪些值得记住，哪些已经过期，重复或矛盾的信息如何处理。一种常见做法是「dreaming」：安排后台任务定期回看近期执行记录，整理并更新记忆。

衡量效果也不该只看存了多少内容，而要看草稿获批是否更快、邮件回复率是否改善，以及 Agent 提出的问题有多少真正促成了行动。

# 人的评审体验，是系统的一部分

LangChain 总结了三个很具体的设计方向。

首先，只呈现值得关注的信息。GTM Agent 把对话分成等待人工处理、需要起草回复和无需回复；Robin 则用 Jev 判断是否有必要加入 Slack 讨论，而不是看到消息就插话。

其次，让结果容易评审。团队发现，在 Slack 里逐条处理待发邮件效率很低，因此为邮件草稿做了专门的评审界面。人的修改不仅是完成审批，也是把难以提前写成规则的偏好反馈给 Agent。

最后，留在已有工作流里。每日简报发到 Slack，后续内容回到同一线程；Robin 先给一两句概要，再展开细节。请求 PR 审查时，附上一行摘要、改动规模和认领按钮，降低接手成本。

这些细节共同决定了：主动式 Agent 是一个可靠的协作者，还是另一个不断制造通知的工具。

## 我的看法

这篇文章最值得借鉴的，是把「主动」拆成两项能力：没有新提示时仍能继续工作，以及继续工作的同时少占用人的注意力。事件和日程解决前者，记忆和评审体验解决后者。

好的长期 Agent，不应只追求运行次数更多，而应让每次问询更准确、每次评审更轻松，并能把反馈用于下一次判断。自主程度的提高，应该建立在这种持续改善之上，而不是简单减少确认步骤。
