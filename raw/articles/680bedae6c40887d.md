## 2 为何要 Super-agent：四特征不是口号

主流 Agent 仍以单个 Session 为工作单元。Session 之间彼此独立；人要并行推进几件事，就得手动切换，并在脑子里维护「哪个窗口装着哪段上下文」。文中观察：一个人通常只能同时跟进 3～5 个活跃 Session。于是：

- 单任务天花板 → 模型能力；
- 多任务天花板 → 人类注意力。

只是给本地单 Session Agent 加 CLI / MCP / 外部连接器，往往仍困在三件事里：单会话同步阻塞、跨任务上下文缠在一起、本机离线执行就停。Super-agent 的目标，是把 Agent 从「人手点开的一次会话」解绑成：跨信道、可持续推进、可并行多任务的连续实体。

## 3 架构深拆：五个模块如何托住四个特征

这是全文主菜。官方总图把系统拆成五大块：双层架构、事件驱动、面向人的交互、计算/状态/执行环境分离、Watchdog。下面按 3.1–3.9 拆开。

### 3.1 总览：不是新理论，是职责切分

[/heydengai/article/2116796865433985385/media/2116783683835428864](/heydengai/article/2116796865433985385/media/2116783683835428864)

读图顺序：先看 Router 不亲自干脏活 → 再看 Thread 直通如何给 Router 减负 → 最后看 Watchdog 与端云分离如何托「持久」。

### 3.2 双层：Router vs Worker

连续性与吞吐量互相打架：

- 所有事件进同一个 Session：上下文最连续，但串行 ReAct 吞吐差，多任务细节混在一起还伤质量；
- 每个事件新开 Session：吞吐高，但缺全局上下文，多会话各自回用户也会吵死人。

解法是职责分层：

Router 层

Worker 层

职责

人类交互、任务间协调、全局记忆

在隔离上下文里执行具体任务

工具姿态

可以不干具体活；甚至可以没有 Bash

满工具集，通常用最强模型

对外说话

统一出口

不直接对外说话，经 Router 回复

模型

往往可用更轻模型换速度

结果质量敏感，倾向最强模型

内部结构

逻辑层；实现上可以是单持久 Session

亦可再开 Subagent / 自己变成 Agent Team

文中一个关键产品判断：让用户手动管理 Session，多半是继承了底层 LLM API 的设计习惯；Session 应是实现细节，不该是用户的认知负担。

实操直觉：Router 像前台值班经理，Worker 像关上门干活的工程师；客户只认前台，会议室纪要（Thread）订好了就不用每封邮件都先经前台盖章。 前台如果自己下场写代码，全局节点立刻变成瓶颈——这也是「Router 可以没有 Bash」这种看起来狠、其实很系统的约束。

内部实现上，文中选了最直白的形态：Router 核心是一个持久 LLM Session。环境事件（Trigger）若在某一轮推理期间到达，会积到下一轮一起处理，形成自然 batching：稳态时一个个进、延迟低；突发时多个 Trigger 合并进同一次 API 调用，长输入短输出的轻量决策能在 prefill 阶段并行，单次请求时长增长往往慢于 batch 变大。后文 Router 压测把这件事量化了。

### 3.3 与 Agent Team 的差别

看起来像「中心节点分活」，但重心不同：

- 典型 Agent Team：主要拆单个复杂任务内部的步骤与角色；Lead 往往要深度理解任务、频繁协调，推理负担重。
- Super-agent 的 Router：只管任务之间的高层关系与分派，不深拆单任务内部。

把差别说得更刺一点：Agent Team 的 Lead 常常「既当导演又当主演」；Super-agent 的 Router 被设计成只当调度台。如果你发现自己的「多 Agent」方案里，中心节点上下文膨胀、工具调用暴涨、还在替成员写细节——那更像 Team Lead，不是 Router。文中甚至反向提醒：用 Prompt 把 Team 主会话管成「不干活只分活」，也能长成双层；标签不重要，职责边界重要。经验上 Router 的工作常没想象中复杂——这是「可用轻模型」的依据。

### 3.4 事件驱动：Trigger、Fast/Slow Path、Thread、订阅直通

驱动源从「人往 Session 里打字」换成半结构化环境事件——群聊、邮件日历、Code Review、CI——统称 Trigger。

过滤：借用系统里的 Fast Path / Slow Path——

- Fast Path：代码按来源、群范围、白名单等确定性规则先砍噪声；
- Slow Path：候选事件再交给模型做语义判断；自然语言策略也落在这一层，方便人用 Prompt 增删规则。

路由：同一 GitHub PR、同一 IM 话题等连续事件流叫 Thread。Router 处理「新任务起点 / 跨任务协调」；一旦 Worker 订阅了 Thread，后续事件由代码直通 Worker，不必再经 Router 工具转发。

订阅是多对多：一个 Worker 可订多个 Thread；一个 Thread 可被多个 Worker 订。同环境交叉时，新事件会打到所有订阅者——没有点对点私聊，也能看见彼此动作，有机会自己处理冲突。输出侧仍向 Router 汇报关键结论，由 Router 回用户并更新全局记忆。

直通的产品含义：全局连续性不等于「每条消息都路过全局大脑」。 连续性由 Router 在「开任务、改归属、跨任务协调、对外说话」这些稀疏节点上维护；密集的同 Thread 跟进，应该变成代码路径上的投递。消融实验后面会显示——在该合成负载下，去掉直通未必让任务更慢，但会让 Router 明显更累（决定次数与 cache-read 上升）。

多对多订阅也埋了一个冲突处理哲学：不先上复杂的 Worker 总线，而是让共享 Thread 的多方同时看见同一事件流，把冲突发现下沉到执行层。这很「操作系统」：中断与信号先送到订户，而不是每颗中断都先排队进唯一超级内核线程。

### 3.5 上下文：Inline & Spill + Chain of Recall

环境事件是连续流，上下文窗口却是稀缺缓存。文中把注入拆成两个基本操作：

- Inline：把很快要用到的信息直接放进当前窗口，少打工具来回；
- Spill：超预算或不常用的完整信息留在窗外，窗内只留引用或摘要，按需再读。

配合局部性：先给对象 ID + 摘要 → 逐步 Inline 近邻（前后消息、回复链、相邻 Review 评论）→ 超限则截断并保留续读入口。

当大量后续事件直通 Worker、Router 又不能把所有历史塞进自己窗口时，同一套 Inline & Spill 推成 Chain of Recall：Trigger / Thread / Worker Session 等对象有唯一 ID；注入时 Inline 相关对象 ID，形成引用图；工具召回时继续带上下一跳的摘要与 ID。模型可以从当前事件沿引用多跳找回旧任务上下文——例如从当前消息读到 Thread → 跟到关联 Worker → 再发现该 Worker 还挂着另一个 Code Review Thread。

这不是浪漫的「无限记忆」，是可工程化的多跳检索约定：承认 Router 不可能把数周任务史常驻窗口，但仍允许用户从另一个信道随口提起旧事时，沿引用图把上下文「钓」回来。Agent 场景里，「浪费窗口」几乎等于「浪费智力」——塞太多，注意力被稀释；塞太少，模型就靠工具来回爬，步数爆炸。

### 3.6 投机执行：先干着，值不值再交卷

借用 CPU 投机执行的直觉：在还不确定结果是否会被用到之前，先根据环境信号在后台干一截；有价值就交付，没有就丢掉，换的是人的等待与打断。

内部 Harness 用户群里的例子很刺激：配置「静默复现并修复」——有人报 bug 或讨论改动时，Agent 先在后台复现、找简单修复；确认问题且修法简单才交 PR，否则全程安静。群里还在吵方案，PR 可能已经在路上。

约束其实很紧：先复现、先找简单修复、确认后才交付。它优化的是「人还在讨论时，机器已经付掉确定性劳动」；没有授权「任何想法都直接强推上主仓」。和 Proactivity 的另一半——不该出手时安静——是同一枚硬币。群聊噪声极高，没有静默策略，主动就会变成骚扰。

### 3.7 面向人的交互：异步 ReAct 与信道礼仪

双层解决了跨信道连续性；真要「连续又高效」，还得解决交互半双工。

经典 ReAct 里同步 run() 会阻塞整环，工具没返回前会话接不住新输入。异步化成 start() / stop()：start() 立刻回 Started，环继续；后台结束再以新事件投递结果；必要时 stop() 砍掉拖太久的后台。该异步任务机制已在 DeepSeek Harness 实现，但尚未默认开启——全双工改变的是交互语义与失败模式（取消、重入、乱序结果），需要更多打磨才能当默认。

跨信道输出要对齐带宽：

- IM：少打扰；需要决策或验收才说话；硬规则试验之一是单次回复不超过约 100 词；
- GitHub / 邮件 / 文档：结构化高密度交付（问题、改动、验证）。

长推理与频繁工具调用关在 Worker 里，不直接泼进群聊。100 词硬规则看起来土，却打中群聊真实带宽：把 IDE 里的长推理瀑布贴进群，是协作事故，不是透明。双层已经把长痕迹关进 Worker；Router 再加信道礼仪，才像「同事」而不像「外接终端」。

### 3.8 存算分离 + BYOM daemon：脑在云，手在本机

本地 Agent 常把「推进 Loop 的算力、必须持久的会话状态、代码仓与工具链环境」绑在同一台机器上——笔记本一睡，Agent 就停。文中两步解耦：

- 算力与状态分离：Loop 放云端无状态弹性容器；Session 等持久状态进数据库。
- 算力与执行环境分离：环境难同步（未提交改动、私有凭据、内网依赖、特殊工具链），那就别硬搬上云；端侧轻量 daemon 不存会话状态，只负责执行命令并回传结果。

这与 Anthropic「脑与手解耦」同构，场景差异是：这里优先接人日常那台可能间歇在线的本机——BYOM（Bring Your Own Machine），也可接按需云主机。云端 Loop 可以继续观察 GitHub；等到你的机器醒来，daemon 再把必须本地的命令补上。

代价与风险也同构放大——凭据、未提交改动、内网服务仍在端侧，云端若被 Prompt 注入或入侵，攻击面横跨设备。所以 §8.4 不是附录客套，是这张架构图的阴影部分。

### 3.9 Watchdog：外部控制回路

长跑分布式系统很难只靠内部逻辑永远可靠。Watchdog 是主系统外的独立控制回路：定时消息驱动；既看 API 错误、状态恢复失败等基础设施问题，也用模型判断 Worker 有没有实质进展、有没有跑偏目标。它本身是带满工具的 Agent Session——维护者可以用自然语言问故障，也可以让它在运行中改主系统行为（加减 Prompt、调 Trigger 规则）。

传统「进程还活着吗」探针不够：Agent 系统更常见的病是还在跑，但在空转或跑偏。外部回路用模型看进展，才能对上 Proactivity / Persistence 的长期运行；自然语言改规则，等于留了一扇「人在环上的系统调用」门。

## 4 实验怎么读：测的是调度，不是你会不会写代码

[/heydengai/article/2116796865433985385/media/2116783691074809856](/heydengai/article/2116796865433985385/media/2116783691074809856)

Router 单独压测（Router 调真实模型，Worker mock）：需决策 Trigger 到达率约 1 → 40 / min 时，平均 batch 1.0 → 2.8，单次请求 2.5 → 3.9 s（慢于 batch 增长），每决定摊销推理 6.4 → 1.6 s。突发排队时，合并处理能提高有效吞吐——这也解释了为何去掉直通抬高 Router 峰值，却未必撞上单 Router 吞吐墙。文中判断：在其当前团队规模下，不必过早分片牺牲全局连续性。

对照里真正刺眼的，是「中性提示下 5 次都不调 Subagent」：单 Session 里把委派交给模型临场发挥，有多脆；双层把「Router 不执行具体工作、Worker 只收订阅 Thread」写成系统不变量，比拼 Prompt 自觉稳得多。「优先委派」能改善，却仍留下「这事够小我自己干」的长尾——Prompt 治理的残差。

读 cache-read 也不要道德化。更高 cache-read 不是原罪，而是用 token 买调度稳定性；去掉直通后完成时间差不多、Router 更贵，说明直通的主收益是保护全局节点，不是魔法加速条。

> 把实验读成「调度稳定性与 Router 开销」，就对了；读成「真实仓库合并率神奇提升」，就越界了。

## 5 仓库边界与 §8 开放问题

原型定位写进 README，值得整段对照：

> Research prototype for reference only, not an official DeepSeek product… much of the engineering done by coding agents… not production-ready… not identical to our internal version or the implementation described in the article… Some designs… are directions for future development and are not implemented in this prototype.

实际能力边界（公开描述）：作为 DeepSeek Harness 的 bundle，面向单个 GitHub 仓库；监听 GitHub，可选飞书；允许的人提出请求 → 开 work item → 独立 session → 例如以 PR 回复；有 web panel 展示需要人看的事项。工作哲学写得很刺耳也很好：尽量少占人的注意力，尽量多交付价值——能帮全队干活的 Agent，也能浪费全队注意力，所以只在被要求或规则允许时行动，只在必须有人决策或能用结果时说话。

公开仓库在 2026-11-01 14:23（Asia/Shanghai） 录得 3871★ / 363 forks。[@OKCX66](https://x.com/OKCX66/status/2116758940641796216) 当日讨论点出 README 先劝退、不少工程由 agent 完成——热度与劝退并存。

§8 开放问题（摘要，不是已交付能力）：

- 双层如何扩展：何时分片 Router、是否引入同层 Worker 直连、长期记忆（跨月）瓶颈；
- Session 之外的人机协作形态：隐藏多会话后，任务如何呈现；过程中如何插手、接管；
- 上下文边界与 A2A：组织级部署等于决定共享/隔离边界；跨实例协作仍是开放题；
- 安全与隐私：事件驱动扩大不可信输入面；云端 Loop + 端侧 daemon 预设互信——一旦云端被入侵或 Prompt 注入，连接设备风险上升；还需要「用凭据但不让凭据进入模型上下文」的机制。

这些开放问题，比任何「对标 Dots」的二手标题都更值得收藏。

易踩坑清单：

- 当成新模型或正式消费级产品；
- 把合成调度实验当成真实 coding 提速；
- 把「开源版 Dots」写成官方定位；
- 忽略 README 劝退与「与内部分支不完全一致」；
- 把 Harness 预览与 Super-agent 原型混成一次产品发版。

## 7 判断与收藏点

值得收藏的部分

- 问题定义准：多任务瓶颈在注意力，不在再堆一个聊天窗口。
- 双层切分清楚：Router 管任务之间，Worker 管任务之内；对外单出口。
- 订阅直通是真系统活：用代码 Fast Path 给全局节点减负，而不是让模型反复当邮差。
- 实验口径诚实：合成负载、测调度；直通省的是 Router token/推理，不一定缩短完成时间。
- 边界诚实：原型、非产品、非新模型、§8 安全与 A2A 未解。

别急着买的部分

- 未公布的费用、官方用户量、内部规模、真实 PR 合并率——本文不编。
- 与 Dots / Grok Bot / Muse 的「官方对标」——社区类比可以记，官方等价声明没有。
- 本机免审批执行——先读 §8.4，再决定你的信任边界。
