Anthropic 常驻 Agent 系列（一）：无人值守时，什么能自己做，什么必须暂停问人？

Agent 可以在后台持续工作，但“能做”与“获准去做”之间，始终需要一道边界。尤其当它持有用户的访问权限，又没有人一直盯着，每一次工具调用都可能涉及文件、外部服务或真实业务操作。

Anthropic 发布的「Building always-on agents」介绍了搭建这类系统的关键组件。咱们分为四篇来分别讨论权限、事件唤醒、通知和记忆。第一篇先看权限：如何让 Agent 自主推进，又在需要人判断的地方停下来。

一、让 Agent 使用凭证，不必让它直接拿到凭证

访问业务系统通常需要密码、API 密钥或访问令牌。如果这些凭证直接进入 Agent 的运行环境，就会扩大泄露和误用的风险。

指南推荐一种部署方式：将代理放在 Agent 运行环境之外。Agent 发起请求时不携带真实凭证，由代理在转发请求前注入。这样，Agent 可以调用授权服务，模型和执行环境却不必直接接触凭证内容。

这里需要分清两件事：凭证保护解决“秘密放在哪里”，行动授权解决“这次操作该不该做”。即使凭证没有泄露，一个经过认证的请求仍可能产生错误后果。因此，凭证代理之后还需要动作层面的检查。

二、自动审核减少打扰，重要决定仍交给人

常驻 Agent 如果每调用一次工具都要等人批准，很难真正承担后台工作。但完全放开权限，又会把风险一起放大。

指南借用了 Claude Code 自动模式的思路：用分类器审查风险较高的动作，拦截被判断为危险的操作，让模型尝试更稳妥的路径；最重要的决定仍需要人工参与。

自动审核的作用，是承担一部分重复的风险判断。它能减少无意义的确认，也可能把一条危险路径挡下来，但不能因此推导出“通过分类器就适合无人执行所有操作”。

对产品而言，需要明确划出自主执行、直接拒绝和请求批准的范围。分类器帮助执行这套边界，哪些后果可以交给系统承担，仍然是一项产品与安全决策。

三、需要批准时，保存会话，结束当前运行

人工审批还有一个容易被忽略的工程问题：用户可能几分钟、几小时后才回复。系统怎样等待，才能既保留工作进度，又不占着执行资源？

先区分两个概念：一次“运行”，是 Agent 被唤醒后连续完成的一段工作；“会话”则保存消息、工具调用等记录，可以跨越多次运行。

指南介绍的延期工具调用，将等待放在会话层处理：

1. Agent 到达需要澄清或批准的工具调用，暂不执行。
2. 保存停在调用中途的会话，结束当前运行，并向用户提出请求。
3. 用户答复作为新事件进入收件箱，启动下一次运行，恢复会话并接入答复。

请求可以通过交互卡片展示，原文以 MCP Apps 为例。等待期间，处理事件的后台进程仍能领取其他工作，不必一直占用资源等用户回来。

这套设计把人工判断接进了异步系统：需要停的是待批准的动作，相关进度通过持久化会话保留，用户回复后再继续。

四、三种机制要配合，不能互相替代

凭证代理、自动审核和延期调用，分别处理不同问题。

凭证代理减少敏感信息暴露；自动审核帮助识别危险动作、减少重复确认；延期调用让关键决定能够交给人，同时保留继续执行所需的状态。

从工程实现进一步考虑，审批还应清楚说明准备执行的动作、对象及影响范围。用户回来时，外部状态可能已经变化，也需要考虑原批准是否仍然适用。这些属于落地时值得补充的约束，不能只靠保存聊天记录解决。

我自己的读后感

常驻 Agent 的自主性，应该体现在授权范围内持续推进工作，也体现在遇到边界时能够可靠停下。

这份指南很值得借鉴的，是将“请人批准”设计成一条可恢复的执行路径。权限检查发现需要人工判断，系统保存进度、释放执行资源，等答复到来再继续。人工参与因此可以自然融入后台工作，而不必让整个流程一直等待。

下一篇咱们讨论事件唤醒：Agent 大部分时间可以休眠，消息和计时器怎样让它及时恢复工作，并避免重复处理与并发冲突。
