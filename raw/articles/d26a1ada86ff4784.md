# 规模起来后，重点转向质量

Uber 的共享 Skills 市场在一年内从 1 个涨到 5000 多个，单月调用量超过 100 万次。规模跑起来之后，真正难的在于如何让这批 Skills 长期稳定，单靠员工写一份好提示词已经不够了。

每个 Skill 用一个目录封装工作流程，里面放说明、脚本和参考资料。模型平时只读名称与简介，执行时再按需加载正文和材料。Uber 用 Git 统一管理版本、负责人和审核，把 Skills 分成团队专用、核心推荐和默认启用三层；再通过统一命令行工具 aifx 抹平 Claude Code、Codex、OpenCode 等不同智能体的安装差异，员工换工具也能沿用同一套 Skills。

# 既测执行过程，也测有没有必要

Uber 建议的评测集构成大约是 5% 固定输入输出样例、80% 真实提示词和 15% 作者判分案例。真实提示词重点检查执行轨迹，看模型有没有选对 Skills、按顺序调用工具以及遵循错误恢复步骤，最终产出则另行评分。把 Skills 放到隔离环境里跑，也能提前揪出隐含依赖作者本机路径、缓存或系统工具的问题。

更关键的一步是做减法：把同一条真实请求分别带上 Skills和不带 Skills 各跑一遍，交给盲评裁判比较答案。在一个数仓查询 Skills 的实验中，不带 Skills 时工具调用多出 13%，工具错误高达 6 倍，耗时多出 31%；带 Skills 的答案赢得了 87% 的比较。这属于单个 Skill 的实验结果，不能直接推成全平台收益；随着底层模型变强，过时的说明甚至整个 Skills 都该及时删掉。

# 把确定步骤交给代码，把失败带回测试

Skills 本身也会加重上下文负担。Uber 过去在默认预加载方式下，光是 100 多个工具的定义，在首条提示发出前就会占掉 5 万到 7 万 token。借鉴 Cloudflare 的 Code Mode 思路，他们改由 Skill 脚本通过命令行和网关调用工具，把大块查询结果存成文件，让模型只读取真正需要的部分，不再把整份中间数据反复塞进上下文。

线上冒出的问题也会回流到迭代闭环里：智能体遇到异常后提交结构化故障报告，交由对应负责人排查、修复并补充评测，发布后再检查回归。人工代码评审里反复卡住的拉取请求，同样会沉淀成新的测试用例。
