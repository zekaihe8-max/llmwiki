# 2026美国AIE大会：Untangle 创始人，1个经理agent带20个builder、每15分钟巡查，招人只看45分钟录屏

11 min read

10 月 14 日，AI Engineer 大会的一场分会场，台上是 Ryan Carson。他介绍自己是 Untangle 的创始人兼 CEO：Untangle 做的是面向家事法的 AI 律师助理，专攻离婚案件。他之前做成并卖掉过四家公司，上一家创业公司做到约 110 人。

结论先说：他的工程团队在云端用 Devin 干活，一个只调度、从不写代码的「工程经理」会话，同时带最多约 20 个 builder agent；他主要靠语音和这个经理说话，从不进 builder 的会话。经理每 15 分钟被自动化强制巡查一遍所有子会话，每个 builder 的审查最多循环 3 次，每个功能上线前他亲自看一遍 agent 录的演示视频。招人也按同一个思路改了：候选人交一段 45 分钟左右的全屏录屏，看他怎么用 agent 做出一个真功能。

下面按他讲的顺序，把这套东西一块块拆开：

- 日常调度：谁跟谁说话、任务从哪来、多久巡一次。
- 质量关：审查几轮、QA 怎么接、录像怎么看。
- 人多了以后：10 个人各带一个经理，再加一个专管合并队列的 agent。
- 招人：每一步怎么走。

### 他为什么拿管人的经验来管 agent

他开场先问台下：谁离过婚？谁认识离过婚的人？最后所有人都举了手。他自己的理由很具体：两个姐妹离过婚，父母也离过婚，「这是人一生中最痛苦的事之一」，他想做点什么让它不那么痛。Untangle 最初是个消费者应用，很快转去做 B2B，现在卖给家事法律所，他说产品和市场已经对上了，增长很快。

他讲这场的出发点是：上一家公司做到约 110 人，他学到很多管人的东西，结果发现「管人就像管 agent」。所以这场讲三件事：Untangle 怎么管 agent，怎么招人（他认为 agent 时代的招聘完全不同了），最后是一个现场演示。

### 一、一个从不写代码的经理 agent

[/FinanceYF5/article/2121800827975454847/media/2121800374613098496](/FinanceYF5/article/2121800827975454847/media/2121800374613098496)

他的「组织架构图」：最上面是人类（每周定优先级、跟客户说话），下面是「Manager agent」，标注 never writes code，人和经理之间是语音对话。来源：AI Engineer YouTube

他先画的是组织架构：人在最上面，定优先级、跟客户沟通，做所有「人的事」。人下面是经理 agent，而他说得很直白：这东西「就是个会话」。

- 工具：他们用 Devin，所有工程都在云端做。他从手写代码一路用过 Cursor，到现在全在 Devin。
- 经理会话：他管它叫 engineer manager（工程经理），它从不写代码，他主要就跟它说话，它下面管一批「孩子」。
- 用语音管它：他说自己读得不快，「肯定不是 agent」，听音频比读文字更能吸收。所以他跟经理基本靠语音，说「我能吸收，能看明白发生了什么，这样自然得多」。

### 二、任务从看板来：一张票，一个 PR

[/FinanceYF5/article/2121800827975454847/media/2121800389075025920](/FinanceYF5/article/2121800827975454847/media/2121800389075025920)

经理 agent 下面是票据看板（Linear），旁注 no ticket, no work；人和经理之间还有「1 question + recommendation」的回路。来源：AI Engineer YouTube

经理主要对着一块任务看板干活，他们用 Linear，他说用什么「不重要」，重要的是它是「要做什么」的唯一事实来源。具体规矩只有两条：

- 每张票对应一个 PR。
- 经理按依赖关系决定先拉哪张票。他自己的评价是：这是「很基础的工程经理活」。

幻灯片上这条链路的细节：人问经理「what needs me?」（有什么需要我？），经理走语音回他，给的是「1 个问题加一条建议」，人答完，经理再往下发票。

### 三、20 个 builder：他从不进它们的会话

[/FinanceYF5/article/2121800827975454847/media/2121800373031915520](/FinanceYF5/article/2121800827975454847/media/2121800373031915520)

看板下面是一排 Builder agents，标注 20 at once、1 per ticket。来源：AI Engineer YouTube

有意思的部分在这里。一个经理同时带最多约 20 个 builder agent。

- 数字是浮动的：他说这个数字在 5 到大约 25 之间变，他们实际能同时管的大约是 25 个。
- 卡点在人：这个数字「某种程度上被你跟经理说话、理解发生了什么的能力卡住」，推得太狠，「很快就会失控」。
- 铁律：经理跟 builder 说话，他从不进这些会话，从不跟它们说话，从不管它们，一切都通过经理。经理平时做的，是回答他不用亲自回答的技术问题，或者解决一些小的卡点。

### 四、每 15 分钟巡一次：写成自动化，不靠经理自觉

[/FinanceYF5/article/2121800827975454847/media/2121800424026238977](/FinanceYF5/article/2121800827975454847/media/2121800424026238977)

图上从经理指向 builder 的箭头标注「checks in every 10 min」。他在台上的说法是：这页写的是 10，但他定的是 15。来源：AI Engineer YouTube

他给经理加了一个自动化，强制它读所有子会话，间隔就是图上这一页的那个数字。他的原话是：页上写 10，但「我决定 15 比较合适」。

他为什么不让经理自己想着去巡：不能相信经理 agent 会自觉做这件事，因为它不是确定性的。所以这本质是个脚本，Devin 自带「自动化」功能，你只要告诉它：每 15 分钟，去读每一个孩子，把事情往前推，让它们保持运转。巡查中冒出来的任何问题，再回到经理那里。

台下他问了一句「有人跟得上吗」，补了一句：我不是说这是火箭科学，但这就是我们现在线上在跑的东西。

### 五、审查最多三轮，QA 是 builder 的子会话

[/FinanceYF5/article/2121800827975454847/media/2121800437011714048](/FinanceYF5/article/2121800827975454847/media/2121800437011714048)

builder 右边是 Reviewer agent，两者之间标注 review 和 fix bugs up to 3×。来源：AI Engineer YouTube

审查。 每个 builder 都有一个它能调用的审查 agent。他说 Devin 自带审查，大概任何代码 harness 都有。他们的规矩：

- 审查最多循环约 3 次。
- 如果三次之后仍然有已经修过却没清掉的重要 bug，builder 就把问题上报给经理 agent；经理有需要的话，再上报给他本人。他说这套看起来效果不错。

QA。 这是他们额外加的一道流程：它会起一个 builder 的子会话去跑 QA。他的态度是：这东西很便宜，「你应该尽可能多地起 agent，只要别拖住你的合并队列」。这套 QA 流程是新加入的工程师 Dale 帮着装上去的，他觉得到目前为止效果不错。

合并队列。他预告大家都会遇到的问题是合并队列变慢：一边是把 PR 一遍遍啄到死，一边是赶紧合进去，要找个平衡。

### 六、录像：每个功能上线前，他亲自看

[/FinanceYF5/article/2121800827975454847/media/2121800420796559361](/FinanceYF5/article/2121800827975454847/media/2121800420796559361)

四步流水线：1 Code + tests（failing test first）、2 QA agent（checks the proof）、3 Video（records it working）、4「Ship it」（a human types it）。来源：AI Engineer YouTube

这是他说「爱了又爱」的部分。

- 谁来录：每个 builder 都会录一段视频，展示功能被使用的过程和测试通过的情况。他们用的 Devin 里这是内置功能，叫 test：先生成测试用例，再录视频，每条用例给出绿色或红色。他说如果你的工具没有，你应该自己做一个，但「很难」。
- 怎么用：只要是面向 UI 的功能，就必须看。全绿的视频能让他确认「我们以为发生的事确实发生了，而且视觉上看着没问题」。
- 人在哪一步：这是「必须由人说 ship it」的那一步。经理会话会告诉他：有个视频等你看。
- 他怎么看：先读一段摘要，搞清这个 PR 是做什么的、应该做什么，再看视频，并且要真看进去：他说这是整套流程里「很难」的部分，要放大、要理解「这个 PR 到底在干什么」。
- 他的提醒：这是你最想偷懒的地方，别偷懒，这是你作为产品负责人必须亲自承担的瓶颈。通常得在笔记本电脑上看。
- 一个小故事：上台前他还在手机上跟经理说话，经理说有个视频给他。他在手机上看，看不清，「非常想说算了，上线吧」，但没有，回到电脑前把视频看完。

他说他们这样以较高的质量发了很多 PR，这套流程迭代了「几百次」。他也说，这套东西明天就会变，一周后可能就没用了，但今天它管用。

### 七、10 个人、10 个经理，再加一个合并队列经理

[/FinanceYF5/article/2121800827975454847/media/2121800504250654720](/FinanceYF5/article/2121800827975454847/media/2121800504250654720)

「The team」一页：外圈 10 个人，每个人配一个经理 agent，经理之间互相连线，标注 coordinate。来源：AI Engineer YouTube

人多了怎么办：假设 10 个人在做事，每个人通常配一个工程经理会话，有时两个，他自己此刻就开着两个。

- 经理之间要能互相说话：他说这在 Devin 里是内置的，别的 harness 大概也有。要求是会话之间能互相通信，并且每个会话都知道其他会话是谁。
- 他的观察：它们很擅长这个，放大看任意一个会话，它们在互相发消息，「清楚、直接、快」，说的都不是闲聊，是为了互相解卡必须知道的东西。他的话是：如果你不允许会话互相说话，你是在拖自己后腿，大概也在交付更差的软件。
[/FinanceYF5/article/2121800827975454847/media/2121800485581864960](/FinanceYF5/article/2121800827975454847/media/2121800485581864960)

10 个经理的圈外多了一个 Merge manager agent，箭头标注 ready to merge。来源：AI Engineer YouTube

即便这样，还是需要一个合并队列经理（merge queue manager）。它负责协调涌进来的一波波 PR：

- 要解决的具体冲突：比如数据库迁移编号，如果所有 agent 都去抢，就会不停相撞。有了合并经理，这类冲突就消失了。
- 它还更聪明地安排合并顺序。
- 它也「只是会话」：不是什么特别的东西，就是 Devin 里的一个会话，他给它们起名字，好知道发生了什么。底下用的是 GitHub 的合并队列，他说「不是火箭科学，效果挺好」。
- 做法的来源：他提到前一个 OpenAI 演讲者说过「要 unhobble（解开束缚）」：定好角色，然后解开模型，让合并经理去「把这些弄得更好」，很管用。

他在这一段还有一句硬话：如果你还在本地写代码，停下来。他要求必须用云端 agent，不管是 Devin 还是别的，「本地开发是在搞砸自己，拖团队的后腿」，因为你做不到上面这些。

### 八、招人：不聊，只看 45 分钟录屏

[/FinanceYF5/article/2121800827975454847/media/2121800499397824512](/FinanceYF5/article/2121800827975454847/media/2121800499397824512)

「How we hire」第一块：Candidates，45-min、whole-screen video、agents ship new feature、app they maintain。来源：AI Engineer YouTube

他的开场判断很重：他说以前招人的那一套，现在全都过时了，没有一条说得通。他们现在的流程如下：

- 不做任何预筛，不开任何视频聊天，在这个流程的大部分阶段不跟人接触。理由：会产生偏见，你会喜欢他的爱好、喜欢他跟你说话的方式、觉得他有意思，「全是噪音，一点信号都没有」。他认为唯一重要的是：他会不会操作 agent。
- 候选人交一段约 45 分钟的全屏录屏。内容是：在一个他们自己已经在维护的应用上，做一个功能，通常是一个 PR。「没有指令，没有指导，什么都没有」，他只想看这个人当 agent 操作员有多好。这一步是免费的，不付钱，算是进门的门槛。
- 把视频喂给排名 agent。给它的指令是：看视频，看转录，给这些人排序。

他说自己第一次这样做时没有信排名结果，不喜欢它给的结论，讽刺的是它是对的：排第一的那个人他本该雇，只是他当时「有偏见」。他的看法是，你完全可以自己把所有视频看完，有时间就看，但他发现足够聪明的模型对「这个人有多好」判断得相当准。

他还观察到几个现象：候选人会含糊嘟囔，或者不说出自己的思路，所以你看不出他在想什么、做什么；也有人话很多。他说这很有意思。

[/FinanceYF5/article/2121800827975454847/media/2121800483392335872](/FinanceYF5/article/2121800827975454847/media/2121800483392335872)

排名 agent 之后是「Top 5」：real PR（our codebase）、whole screen recorded、fixed fee、max 16 hours。来源：AI Engineer YouTube

- 取前五名，邀请做一个有偿项目。付固定费用，占用对方 16 小时；给对方一个 Devin 席位；要求把一个真实的 PR 做到可以合并；让对方签 NDA；全程录像（他们用 Loom）。
- 把这 16 小时的视频喂给 Devin，问它：我们该选哪一个？他自己上一轮把这 16 小时的视频全看了，说「很折磨」，但确实给了他一个对这些人的好判断。
- 最后才打电话。挑出几位入围者，之前不通话（通话会让你有偏见、困惑、想去选不该选的人），电话里就一句：我们想雇你，聊聊。他说你看了几个小时的视频，其实不太需要这通电话，但有一点人和人的连接是重要的。

他的结论：他雇过「几百几百几百」人，这个方法「更容易、更好」，他认为大家都会往这个方向招人。

### 收尾

他在最后留了两句，一句是联系方式：想了解 Untangle 去 untangle.us，他在 X 上「一直都在」，已经在 X 上 20 年；对家事法有兴趣、想让离婚没那么痛苦的，可以找他。想了解「带公司、管 agent」的，也在 X 上。另一句是前面已经提过的：这一套流程，明天会变，一周后可能没用了，但今天它管用。他提前 3 分钟结束了这场。
