Cognition 推出 Devin Bots：从接单写代码，到带领多个 Agent 持续负责一项工程目标

Devin Bots 想解决的不只是「Agent 能不能完成这次任务」，是任务结束之后，谁来发现下一件事、检查效果，并继续推进。

与一次请求对应一次执行的 Devin 会话不同，Bot 是持续存在的工程队友：拥有独立身份、记忆和工具权限，能拆解目标，启动多个 Devin 会话并行工作，再跟进测试、代码审查和后续改进。

# 交给它的不是工单，是一项职责

一个很直观的区别：不要求「把这个功能移植到 Android」，让 Bot「持续保持 Android 与 iOS 的功能对等」；不「修复这次布局跳动」，而「在产品不断改动时，持续保持页面流畅」。

前者交付一次就结束，后者需要不断发现差距、安排工作、验证结果。Devin Bots 把这层持续协调也纳入了产品。

Bot 可以按日程运行，也能由工具里的事件触发，例如关注 Slack 中的客户问题、每晚检查 CI，或跟进 Linear 中的阻塞事项。创建时可以从 QA、产品开发、性能优化等模板起步，再配置具体职责。

# Bot 负责统筹，Devin 会话负责执行

每个 Bot 有一条持续对话，承接目标、反馈和进展。它拆出的具体工作，会在独立云端机器上启动 Devin 子会话，执行方式与工程师直接启动 Devin 相同。

这里有两种长期信息：一类是人设定的指令，明确职责和工作方式；另一类是 Bot 在工作中积累的记忆，包括偏好、纠正和项目细节。共享给团队后，大家可以围绕同一个 Bot 协作，不必每次重新交代背景。

Bot 之间也能派活。官方演示中，QA Bot 发现问题后交给 Developer Bot 修复，再回来验证。人不需要手动搬运每一步上下文，而是重点处理目标调整和关键判断。

# Android 应用案例，展示了持续负责的含义

Cognition 的 Android Bot 在没有专职 Android 工程师的情况下，用 44 天做出了 Devin Android 应用，合并 1134 个 PR、关闭 1217 张工单，编写约 34.5 万行 Kotlin。

期间负责人共发送 183 条消息，约每合并 6 个 PR 才发一条消息，其中 22 天完全没有发消息。应用已进入 Google Play 开放测试，Bot 仍在继续跟进功能和测试反馈。

另一个 Layout Bot 每三小时构建主分支最新代码，查找并修复布局跳动。三周内合并了 159 个相关 PR，团队称卡顿降低了 70%。这比单次生成演示更能说明产品方向：职责不会随一次会话结束而消失。

# 效率数字之外，更重要的是人如何介入

Cognition 表示，内测用户平均每条消息对应的已合并 PR 数量达到此前的 4.5 倍。Jenny Xu 则用约 20 个 Bot 协作运转游戏工作室，主要与负责总协调的 Super Jenny Bot 沟通，每天从手机查看四次；每周 PR 数量由约 50 个增加到 1900 个，并保持每周发版。

这些数字体现了任务并行和协调方式的变化，但 PR 数量并不直接等于软件价值，仍要结合功能交付、质量和维护成本来看。

需要批准、选择方案或审查的事项，会集中到 Needs You。Bot 使用自身配置的连接和密钥，不会因为某个人给它发消息，就自动继承对方权限；共享时也能区分使用、配置和分享权限。新增访问权限或自动化需要先征求同意。

产品已开放使用，用量计入创建者所在方案；Teams 和 Enterprise 可以设置花费或计算用量上限。
