Shopify：移动应用出码提速 11 倍后，用攻击面地图把安全审查拆到单条深链

来自 [@ShopifyEng](/ShopifyEng) 工程团队博客，在 Agent 时代，他们移动应用的代码吞吐已经是去年同期的 11 倍。12 周重写 Shopify 应用期间，平均每周改动约 43.4 万行，去年同期大约是 3.9 万行。现有漏洞扫描已经会检查改动过的代码，他们还想把攻击面压小，并把已经学到的做法固化下来。

先给每个应用画一张攻击面地图

每个应用都维护一份安全敏感清单，按深链、WebView、本地存储、权限、依赖等分类。每条会写清为什么重要，并附上结论和对应代码链接。结论只允许五种：修复（带严重程度）、权衡、安全、已修复、仅调试。

地图由一组 Skill 生成，每个类别一种 Skill。起点是 OWASP 的移动应用安全标准 MASVS 和测试指南 MASTG，再叠上他们处理过的漏洞，包括自己应用里出现过的问题。Skill 会写清要列出什么、什么样算合格、该检查什么。定时审查、一次性安全评审，以及在代码里工作的 Agent，都可以加载同一套 Skill；学到新东西就更新 Skill，之后每次运行都会带上。

一次只审一项，每个工作日对照变更

如果让模型在整个应用里找漏洞，得到的往往是又长又含糊的清单。所以每个 Skill 会先做完整盘点：每条深链路由及它读取的参数、每个 WebView 及其加载的主机和 JavaScript 接口方法、每一项 Keychain 和 Keystore 条目、每个依赖及其版本。然后模型一次只审一项，并且只看这项相关的代码。以深链为例，就是看一条路由、它读取的每个参数，以及参数被恶意构造时会发生什么，答案要具体到可以核对。若还要判断是否真的可被利用，可以把这个问题交给前沿的网络安全模型。处理事故或 HackerOne 报告时，他们会先修漏洞，再把这类问题写进 Skill，之后每次运行都会拿当前代码对照。

每个工作日，模型会查看应用的改动并更新攻击面：先把最新提交的盘点与上一版已接受的地图对比，只有被引用的代码行变了，或盘点结果本身变了，才算这项发生了变化；再只用只读工具、只根据代码，给每项新增或变更做出判断，并扫一遍改动文件，看有没有地图尚未覆盖的安全相关内容；每条回答都会检查格式、行号范围、措辞，并确认不含密钥；最后生成新地图和变更页，在 Slack 发摘要。有些问题不会出现在自己的改动里，Agent 会定期阅读安全新闻，对照地图和代码检查，发一份简短简报，只有真正影响到他们时才提醒团队。同一套 Skill 也用在引入第三方库之前。

这些检查是对 Dispatch 的补充。Dispatch 是他们的 Agent 漏洞扫描器，负责在改动过的代码里发现并证实漏洞；攻击面地图则保证整个应用保持较小的攻击面，并遵守既有做法。每发现并修复一个漏洞，下一次检查就会更严。
