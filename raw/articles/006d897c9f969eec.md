Amp 团队是什么工作的？

21 人、一周一次会、无季度目标、几乎无头衔、无 PR、无强制代码评审、直推 main、一天约百次发布、分钟级修 bug，靠信任和 Agent 而不靠流程。

来自 [@sqs](/sqs) 和 [@thorstenball](/thorstenball) 播客「The Company of the Future」，他们把 [@AmpCode](/AmpCode) 本身当成工作方式的一部分：小而熟、无部门地盘、周一对齐后各自写周目标，用 WIP / shipped / orb good / orb bad 频道和特性开关同步；质量靠「先让 Agent 给出端到端证据」和全员用产品，而不是靠强制 PR。前提反复强调：人少、彼此校准过、以营收与产品共同成功为动机；这不是把 2019 年 250 人组织乘上 AI 就能复制的模板。

Amp 团队画像
约 21 人，这种形态大约一年；二月招过 Hamish 后基本不再招人（纽约想招 FDE）。无部门、无一堆高管层级，「人人几乎什么都能做」；有所有权，但没有「这块地只有我能动」。自称人均营收不错，对手编制大很多倍也能打到相近体量。Quinn 曾任 Sourcegraph CEO，Thorsten 从约 19 人跟到约 300 人扩张；他们强调 Amp 从 Sourcegraph 拆出，就是为了保持这种规模与速度。

一周是怎么过的
· 周末：修 bug、听反馈；Thorsten 常写 Sunday post（大约一年二十多篇），点出最重要的事或「继续这样做」；Alex 发周数据。
· 周一：同一场会对两遍，欧洲早上约 8:30（含澳洲约 5 人），约 8–9 小时后再开旧金山场。除 Quinn / Thorsten 两边都参加外，其他人每周固定会议只有这一场。约一小时：先自由讨论优先级（无脚本化各部门汇报），末尾静默在 Google Doc 写本周目标并口头念标题；会追问新闻稿、打算哪天发。
· 没有季度主题去硬套；动机是把产品做出去并赚钱，而不是「对齐领导两个月前定的口号」。分工靠「做什么给你能量」自然落下；模型上线有人盯、基建有人深耕，但多是虚线，不是领地。Hamish 做原生 iOS / macOS 并非路线图三件套，而是先 spike 再说服团队。

协作频道与「敢砍功能」
四个关键频道：work in progress（举手我在做啥、求反馈、发新闻稿草稿）、shipped（已上线）、orb good / orb bad（内部正负反馈；坏反馈要直说，不要先找银 lining）。大改动常要求先写对外新闻稿再发——写不清楚就说明问题或方案还不对。功能多先挂 feature flag，全员试用，再决定全量、改、或删；删掉也会在 shipped 里说一声，且常被庆祝。全员看客户反馈；基建的人也会直接读客户频道找痛点。Thorsten 曾因刷 bug 太多被「踢出 bug 频道」，改由 Nicolay 分派。

怎么审、怎么发
口头禅式提示：先让 Agent 给「端到端不可辩驳的证据」，测试矩阵、数据流、截图 / 录屏；再决定要不要看代码。热路径才抠性能与结构。用 Amp 多人 Thread 拉同事进同一线程改方案。

无强制 PR / 人工代码评审；可自看、可找人帮忙。主干开发：推 main，CI 绿就自动部署，官网服务几乎每次绿就发，平均约 90 次/天；从进 main 到全员可用约 7.7 分钟（他们还想再压）。CLI 等有的两小时一批。靠小步提交 + 特性开关 + 先埋日志再改实现来降风险；Agent 可读生产日志（OIDC / 限时授权），部分只读库进 BigQuery。修 bug：Slack 一键开 Thread → 看诊断包与日志 → 人确认再发 → Agent 等滚动完成再给用户发「已修好 + 积分」邮件。

他们怎么看更大公司
Agent 把工程师「翅膀」拉宽后，按 2019 编制划的地盘会互相撞；不是每个职能都该乘 10。对卡在私密吐槽群里的人：关掉闲话、直接跟愿意改的 CEO 说；有一点点流程摩擦，体感也会差很多。两人承认：21 个已磨合过的「联合创始人」是历史偶然，从两个人冷启动或从 300 人压到高能动密度，路径仍不清楚。
