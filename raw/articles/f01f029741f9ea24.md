# Harness 是让模型持续工作的配套系统

讨论中一个比较清晰的解释是：模型负责推理和生成，harness 则负责把模型接进实际工作。

它管理上下文、提供并执行工具、保存运行状态、处理失败和重试，并决定什么时候停止、什么时候需要人工批准。Claude Code 本身就包含这样一套面向编程的运行框架，并不是“裸模型”。

因此，自建 harness 未必是在复制聊天界面或代码编辑器，也可能只是为特定任务设计更合适的执行循环、工具接口和控制规则。这里讨论的是 Agent 运行框架，不是负责出题和打分的评测框架。

# 为什么不把规则都写进 CLAUDE. md？

发帖人也追问：把仓库规范、测试要求和权限限制写进说明文件，不就够了吗？

高赞回应强调了一个重要区别：告诉模型应该怎么做，与由系统限制它只能怎么做，不是一回事。

例如，“生产操作前必须审批”可以写进提示词，但真正可靠的限制，需要工具或权限系统拒绝未经批准的操作。类似地，费用预算、数据访问范围和审计记录，也不能只依赖模型记住要求。

不过，这不意味着 Claude Code 只有提示词约束，它自身也有权限控制。企业真正需要判断的，是现成机制能否覆盖自己的要求，而不是一看到硬约束就必须从零开发。

# 企业需要的，可能只是适配而非重写

支持定制的评论主要关注内部系统、持续集成、评审流程、数据权限和成本控制。这些需求未必能直接套用通用编程助手。

一个很具体的例子是处理测试输出：先截取与失败有关的信息，避免把整份冗长日志交给模型，既减少上下文占用，也降低费用。这类工程工作不改变模型，却会影响它完成任务的效率。

# 我自己的想法

需要把两个问题分开：模型有没有能力完成任务，系统能不能让它在规定条件下可靠完成任务。

Harness 主要处理后者。企业是否需要自建，应从现成工具覆盖不了的具体约束出发。能通过配置、扩展工具和接入内部流程解决，就不必重写整套框架；只有运行方式确实不同，定制才有明确价值。
