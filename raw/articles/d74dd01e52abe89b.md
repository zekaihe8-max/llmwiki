折腾了这么多 MCP，我越来越觉得，Skill 才是更值得优先研究的方向

最近看到不少人在讨论 MCP 和 Skill 到底该怎么选，结合 Pi 一开始的观念是直接在MCP对立面的就感觉有必要聊一下

我自己不管是在 Claude Code、Codex，还是 Pi Agent、Hermes Agent 这些工具里，前前后后都接过不少 MCP，也写了不少 Skill

在这个过程中发现，很多人一上来就喜欢装十几个 MCP，觉得装得越多 Agent 越强，但是实际跑起来，效果往往还不如几个简单的 Skill

我总结下来，一般出在这几个问题上

1、首先是上下文占用太大

很多 MCP 只要一接进去，不管你这次任务用不用得上，一堆工具说明就会直接塞进上下文里，还没开始干活 Token 就先被吃掉一大截

相比之下 Skill 是按需加载的，平时几乎不占地方，真正用到的时候再读 SKILL.md，对上下文要友好得多

2、其次是很多人把用途搞反了

这方面我自己以前也踩过坑，什么需求都想先找个 MCP 装上，后来才发现 MCP 更适合去接外部数据和接口，比如查库或者调线上服务

但是日常干活的时候，Agent 缺的往往不是接口，而是你告诉它具体该怎么一步步做事，这种事直接写个 Skill 配合本地命令，反而比 MCP 顺手得多

3、最后是维护和排错太折腾

这也是我觉得很容易被忽略的地方，MCP 装得太多，模型有时候根本不知道该调哪个工具，而且动不动就遇到环境报错或者服务连不上

修工具花的时间比干正事还久，如果缺少克制，装了一堆用不上的插件，反而会把整个 Agent 拖垮

所以我现在越用越简单，真需要接外部系统的时候才上 MCP，剩下的工作流和规范全部尽量用 Skill 解决

我希望后面不管是开源工具还是国产的 Harness，都能把 Skill 的生态做得越来越好用，把上下文留干净，Agent 干活才能真正稳下来
