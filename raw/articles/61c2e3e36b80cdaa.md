# Grok Bot 怎么用才顺手？拆解 poteto 的使用指南

5 min read

poteto（lauren）的这份 Grok Bot 指南，从创建 bot 讲到日常协作和自动化。它值得拆的地方，是这些建议怎样配合起来，让 bot 少猜、让人少返工。[主帖](https://x.com/poteto/status/2116576229319233596) · [补充帖](https://x.com/poteto/status/2116580481236115933)

先把帖子用起来，再看背后的设计。

### 把帖子交给 bot，先改一件事

打开 Grok Bot，发给它主帖和补充帖，再加上这段话：

plaintext

```
请阅读 lauren（@poteto）的 Grok Bot 指南和补充帖： https://x.com/poteto/status/2116576229319233596
https://x.com/poteto/status/2116580481236115933

请结合我的情况，找出最值得改进的地方，选一件适合先试的事，
告诉我需要提供什么、你准备怎么做，以及怎样检查结果,
信息不足就先问我
```

> 如果它不了解你的工作，再补充现有分工和最常卡住的环节。这样得到的建议才有具体落点。

[/0xlangeai/article/2117197419779866647/media/2117188649414787073](/0xlangeai/article/2117197419779866647/media/2117188649414787073)

这次回复选中了“少而精”：先清点空壳和职责不清的 bot，再确认哪些需要保留。它也给出了检查标准——每个留下来的 bot，都能用一句话说明负责什么、不负责什么。

你可以照这个方式，选一件事试做，检查结果，再继续调整。需要新角色时，再找作者推荐的 [Dr Eggbot](https://x.ai/bot/_jOdbfkB16zxu7MRcmReE)设计。

### 好设计，是让 bot 少猜，也让你更容易检查

一句“帮我做内容”，留下了很多决定：优先追热点还是核实资料？交选题还是写成稿？证据不够时怎么办？这些没说清，bot 就得替你补。

我认为这套方法的价值，在于提前明确关键决定，并让执行过程可以检查和修正。职责减少目标冲突，边界规定何时停止，复述暴露误解，skill 保存确认过的做法。

[/0xlangeai/article/2117197419779866647/media/2117188673632702464](/0xlangeai/article/2117197419779866647/media/2117188673632702464)

“更好”最终应该体现在同类任务里：少遗漏、少返工、少重复解释。下面分析的是设计逻辑，实际改善仍要靠使用结果验证。

### Dr Eggbot：先设计岗位，再创建 bot

[公开介绍](https://x.ai/bot/_jOdbfkB16zxu7MRcmReE)写得很明确：Dr Eggbot 会询问偏好，再调用 CreateAgent 创建 bot。非编程 bot 的要求是一个职责、一种口吻、明确不做什么、不留多余工具；编程 bot 还强调去掉 AI 套话和验证结果。

[/0xlangeai/article/2117197419779866647/media/2117188673670352896](/0xlangeai/article/2117197419779866647/media/2117188673670352896)

它把创建时需要考虑的标准放进一个可交互的工具。用户可以从熟悉的工作讲起，不必先学会写一份完整的 bot 配置。这降低了起步的负担，但设计是否合适，仍要看实际产物。

下面这次操作里，当前 bot 先将需求收紧为“只找 AI 工具／使用经验选题，不写稿、不发帖”，再转交 Dr Eggbot。返回消息报告已创建「AI选题」，并说明结果交给推助手或内容主笔。

[/0xlangeai/article/2117197419779866647/media/2117188880286015488](/0xlangeai/article/2117197419779866647/media/2117188880286015488)

这张图展示了职责、边界和交接对象怎样明确下来。它没有展示 Dr Eggbot 的追问过程，也没有展示最终配置；两个角色做的事，需要分开看。

### 一个职责，让目标更容易取舍

让一个 bot 同时核实资料、追热点、写传播文案，遇到“很有话题性但证据不足”的消息时，几个目标就可能冲突。

把任务收紧到“交付有来源的选题简报”，检查就有了重点：来源是否支持结论，哪些地方待核实，为什么适合你的读者。出错后，也更容易找到该改哪一步。

[/0xlangeai/article/2117197419779866647/media/2117188893284212736](/0xlangeai/article/2117197419779866647/media/2117188893284212736)

职责收紧会减少覆盖范围，也别拆得过细。收集、去重、核实可以共同服务一份简报；每一步都建一个 bot，反而增加交接。这也是“单一职责”和“少而精”要一起用的原因。

### 边界和工具，要与职责一致

“负责选题”还没回答：能否顺手写稿、能否发布？明确“不写稿、不发帖”，就给出了停止位置。资料不足时标记待核实，也是在规定一种可接受的结果。

工具配置应该对应这些边界。研究需要读取资料，就保留必要的读取能力；不负责发布，就检查是否还留着不需要的发布工具。这样既容易审查，也能减少无关的行动选项。

[/0xlangeai/article/2117197419779866647/media/2117188905648926720](/0xlangeai/article/2117197419779866647/media/2117188905648926720)

一种口吻主要减少反复改表达的成本，不能保证事实准确。验证结果则要求拿出可检查的依据：配置是否真的写进去了，试做是否符合标准，而不只是回复一句“建好了”。

### 复述检查理解，小样检查执行

poteto 推荐用语音或转写集中讲背景，最后让 bot 用自己的话复述。这两个动作解决的是不同问题：前者方便把经验说出来，后者让理解偏差显现。

例如，你说“有新信息”，它理解成“最近一天发布”。简单回答“明白了”看不出这个差异，复述却能让你在它开始工作前纠正。

[/0xlangeai/article/2117197419779866647/media/2117189465219444736](/0xlangeai/article/2117197419779866647/media/2117189465219444736)

理解一致后，再让它做一份小样。把标准复述正确，不代表能按标准执行；实际的来源、事实和判断，仍要检查。

### 把纠正留下来，下次才有机会少返工

poteto 建议，在告诉 bot 怎么做任务时，让它把方法写成 skill。实际做过一次，才容易发现需要补的规则：同一事件合并处理、保留原始链接、未开放的功能注明状态。

把这些整理成可以修改和调用的工作说明，下一次才有依据可循。结果有问题，也能检查规则是否写清、是否被调用，再定位执行上的偏差。

[/0xlangeai/article/2117197419779866647/media/2117190349961728000](/0xlangeai/article/2117197419779866647/media/2117190349961728000)

只保存长期适用的做法，别把“今天只看某个产品”也变成固定要求。私有 GitHub 仓库便于独立保存和版本管理，但保存以后，还得换一批材料试一次，确认 bot 能读取并沿用规则。

### 下一步改什么，看你还在手动做什么

原帖还让你留意反复复制粘贴的地方。这个切入点很实用：答案生成得快，不代表整项工作省时；资料怎么进来、结果怎么送出去，也算你的时间。

做法稳定以后，再用连接器接通信息流，让脚本处理固定步骤，根据需要安排 routines。poteto 同时提醒控制触发频率、先过滤订阅事件；她推荐定时任务最高到每小时一次，这是使用建议，并非产品限制。[补充帖](https://x.com/poteto/status/2116580481236115933)

团队共享也一样，值得复用的是已经调顺的职责、规则和工具。先让一个 bot 稳定接住一项工作，再逐步扩大范围，才容易看清每次调整是否真的减少了返工。
