Together 团队分享 Agent 评测实践：失败的不只是模型，还有文档和 Skills

[@togethercompute](/togethercompute) 团队 [@nutlope](/nutlope) 分享了团队里的实际做法：用 Coding Agent 测试自家 SDK、命令行和文档，再根据失败记录改产品。

[together.ai/blog/how-we-do…](https://t.co/twv0g8DM5W)

# 评测的对象，是 Agent 使用产品的全过程

团队把真实开发需求写成任务，例如查询 GPU 集群的可用区域、找到最便宜机型，再生成预订命令，但明确禁止真正下单。

同一任务比较三种配置：只给提示词、接入文档 MCP，以及提供 Skills。Agent 在沙箱里运行，由 GitHub Actions 编排，同时记录 API 调用，再由模型裁判判断通过、未完成或失败。

他们不仅看失败记录，也复查成功轨迹：最终做成了，不代表文档清楚、路径合理，Agent 可能只是反复绕路后碰巧完成。

# 两句话，能比换模型更值得先做

早期一项 GPU 集群任务中，Sonnet 4.6 即使使用 Skills，也只成功了 15 次中的 4 次；同配置下，Opus 4.8 成功了 14 次中的 13 次。

原因不全在模型：Agent 把命令行示例输出当成实时库存，Skill 又把它引向营销页，而非价格表。团队补充两句话，明确指向实时区域接口和价格表后，该任务在 Skills 配置下对所测模型全部通过。

评测还发现，错误信息指向不存在的接口，以及重试请求异常返回 404。只测最强模型，反而可能掩盖这些产品问题。

# Skills 整合，也可能越改越差

团队将 14 个分散的 Skill 合并为统一入口，首次结果却退步：72 次运行仅通过 54 次，未完成次数从 7 次升至 18 次，单次费用翻倍。

压缩入口说明、更新过时模型并修复示例后，72 次运行通过 70 次，约为 97.2%；平均耗时下降约 20%，费用回到原先水平。

这说明，统一入口并不天然降低使用难度。Agent 能否找到正确说明、示例是否有效，都需要实际运行验证。
