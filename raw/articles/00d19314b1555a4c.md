一个月交付上千个 PR，关键不是同时开多少个 Agent，而是你有没有把项目改造成它们能自己检查、少犯重复错误的环境。

做 Grok Bot 的工程师 Lauren（[@poteto](/poteto)）这段38分钟分享，值得拆的是下面这套方法。

1. 先让 Agent 能证明自己做对了（08:44）

她把运行应用、采集性能追踪的流程做成验证技能，里面放可复现的命令行工具，通过 Chrome DevTools Protocol 获取真实数据。

这比要求它「改完记得测试」具体得多：工具能不能跑、性能有没有改善，都有证据，不靠 Agent 在回复里说已经修好。

可以照着做：把你每次验收都要重复的操作，先做成 Agent 能调用、能读懂结果的工具。

2. 给它一张应用功能地图（10:19）

同事在 Slack 丢一张局部截图、配几个问号，人可能知道在说哪里，Agent 未必知道。

她的做法是维护 feature map：记录应用有哪些功能、怎么进入、相关快捷键和页面元素，放进技能目录，并用自动化维护。

这样 Agent 收到模糊反馈后，不必每次从整个仓库里猜位置，还能配合工具进入对应页面验证。

3. 把工程经验写成可执行流程（13:20）

她把调试、功能开发、原型设计等做成一组技能和 playbook，称为 PStack。

这里要分清两件事：流程技能告诉 Agent 怎么查，验证技能告诉它怎么确认结果。只教步骤、不提供检查手段，最后还是得人来兜底。

4. 同一个错误反复出现，就别继续补提示词（15:40）

她更信任的顺序是：先改代码结构，让错误难以发生；再用编译器、lint、CI 拦截；之后才是规则、技能和审查提醒。

风格指南最弱，因为往往要等人审代码时才发现违规。

这点很实用：每次 review 都在提同一个意见，就该考虑能不能变成自动检查，而不是继续复制那句提醒。

5. 旧补丁会变成 Agent 的新范例（23:02）

她观察到，Agent 会拿附近解释临时补丁的注释当理由，继续沿用绕路方案。补丁越积越多，慢慢就成了默认写法。

他们因此在自己的 Dune 框架里选择禁用注释。这不是所有项目都该照搬的规定，背后的重点是：代码库本身就是 Agent 学习的上下文，坏范例也会被学走。

所以要有人持续清理技术债，把推荐做法收敛到一条清楚的路径。

6. 验证可靠了，再接事件自动跑（32:41）

最后才是通过 Grok Bot 连接 Slack、Sentry 等信息源，用例程触发任务，让 Agent 自动复现 bug、开启修复 PR。

注意，分享讲到的是自动复现和开 PR，不是证明可以无人审查、自动合并。

整套流程最值得学的，是把每次人工纠错留下来：能变成工具的做工具，能变成检查的做检查，能从结构上消除的就改结构。否则开更多 Agent，只会让你同时审更多问题。 [x.com/poteto/status/…](https://x.com/poteto/status/2102050467505430555/video/1)
