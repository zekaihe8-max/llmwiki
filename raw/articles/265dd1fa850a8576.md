# 万字长文拆解 Agent 记忆：40+ 开源记忆系统全面对比

30 min read

40+ 开源记忆系统全面对比：9 种原型 · 架构亮点 · 选型决策树

挑 Agent 记忆，很多人先盯检索、embedding、跑分。真正把系统拖垮的，往往是另一件事：记忆是怎么写进去的，旧事实怎么作废。 选错了写路径，再高的跑分也挡不住过时事实被当成真相。

市面上的开源记忆项目已经远不止「几个热门名字」。它们看起来都在做长期记忆，分水岭却不在向量库选型，而在写路径和存储形态：有的只增不改，有的写时合并，有的做时序作废，有的干脆让 Agent 自己改文件系统。

这篇按这个切法，把 40 多个开源项目归成 9 种设计原型。每个主讲项目用同一套结构写：是什么、架构、亮点、适用场景、外部评价、许可与定价——方便直接对照选型，而不是再攒一份名单。

> 一句话先钉死：Agent 记忆 ≠ RAG。 两者共用 embedding、混合检索、rerank 这些零件，但记忆要解决的是「关于用户和 Agent 自身的事实如何累积、更新、遗忘」，文档 RAG 要解决的是「一堆相对静态的资料怎么找得准」。

方法声明：GitHub 星标是 2026-11-01 约 19:15（北京时间）的 API 快照，只代表关注度；文中所有基准分数都是项目方自报，不同项目用的 judge 模型、提示词、子集都不同，不能横向排名；新加入主文的项目都读过其官方 README 与 LICENSE；外部评价尽量附来源，利益相关方会标出。

## 先搭骨架：Agent 记忆到底分几层

产品之前先讲架构，否则后面所有对比都会变成参数表。

### 按时间尺度分三层

[/heydengai/article/2117114445667442858/media/2116884193661849600](/heydengai/article/2117114445667442858/media/2116884193661849600)

图1 工作 / 短期 / 长期记忆三层

- 工作记忆：模型这一步能看到的全部 token。它是唯一真正「生效」的记忆，其余都要搬进来才算数。
- 短期记忆：一次会话内的历史。框架里的 thread、session、checkpoint，以及上下文快满时做的摘要压缩，都在这一层。
- 长期记忆：跨会话存在的东西。本文讨论的大多数项目，主战场都在这里。

### 写路径光谱：产品真正的分水岭

[/heydengai/article/2117114445667442858/media/2116884196081983488](/heydengai/article/2117114445667442858/media/2116884196081983488)

图2 写路径光谱：门控、抽取、合并、时序作废与自编辑

五种写法，各自对应一类失败：

- 门控写入：漏记。用户没说「记住」，重要信息就丢了。
- 只增不改：新旧事实并存，全靠读的时候排序选对。Postgres 14/16 的事故多半出在这里。
- 写时合并：一次 LLM 判断决定覆盖还是新增，判断错了就静默丢失真相，而且往往没有审计痕迹。
- 时序作废：最适合「什么时候什么为真」，代价是图谱的搭建和运维成本。
- Agent 自编辑：最透明、最灵活，但记忆质量取决于 Agent 自己的判断力和纪律。

> 选记忆系统，先问三个问题：谁决定写什么？新旧冲突怎么处理？写错了能不能追溯和回滚？ 回答不了这三个问题的项目，跑分再高也只是 demo。

### 隔离与共享

多用户产品里，记忆串租户是事故级问题。常见的隔离维度有 user_id、agent_id、session_id、project_id，以及 CrewAI 的层级 scope 树、Mastra 的 resource / thread、Honcho 的 workspace / peer、OpenViking 的 viking://user/ 与 viking://agent/。多 Agent 协作则要反过来：哪些记忆该共享给整个团队、哪些只属于某个 Agent。TencentDB Agent Memory 的 private / team / restricted 三级可见性是目前开源项目里做得最细的之一。

图3 开源 Agent 记忆的九种设计原型

## ① 抽取层：在对话旁边挂一个「事实提取器」

最主流的原型。应用把对话丢给记忆层，记忆层用 LLM 抽出事实、存起来，下次按查询召回再注入提示词。接入快，是大多数团队的第一站。

### Mem0：星标第一的通用记忆层

是什么：面向 Agent 的长期记忆层，有 Python/TS 库、自托管服务和托管平台三种形态。[mem0ai/mem0](https://github.com/mem0ai/mem0)，6.8 万星，Apache-2.0。

架构：抽取 + 检索两段式。开源 v3 改成单次 LLM 调用、只增不改（ADD-only），冲突交给读时排序；检索融合语义向量、BM25 和实体匹配。论文版（[arXiv 2504.19413](https://arxiv.org/abs/2504.19413)）曾是 ADD / UPDATE / DELETE / NOOP 的写时合并，[v2→v3 迁移文档](https://docs.mem0.ai/migration/oss-v2-to-v3) 记录了这次转向。图记忆和时间元数据主要在托管平台（[Graph Memory 文档](https://docs.mem0.ai/platform/features/graph-memory)）。原 OpenMemory MCP 已并入主仓生态，让 Claude、Cursor 等客户端共享一份本地记忆。

亮点：几行代码接入；混合检索；部署形态最全，生态集成最多。

适用场景：给聊天产品、客服、个人助手加用户级个性化。不适合吞企业 PDF 当知识库。

外部评价：几乎出现在每一份 X 清单上。实践者普遍认可「托管省事」，抱怨集中在抽取出的事实脆弱、自托管与平台能力有差距、基准对比有争议（HN 上有关于基准公平性的讨论）。ADD-only 意味着时效性依赖读时排序，正是「新旧事实并存、读时挑错」的高发区。

许可与定价：开源 Apache-2.0；托管平台有免费额度和付费档，以 [mem0.ai/pricing](https://mem0.ai/pricing) 为准。

### Hindsight：让 Agent「学会」，而不只是「记住」

是什么：Vectorize 出品的 Agent 记忆系统，[vectorize-io/hindsight](https://github.com/vectorize-io/hindsight)，5.7 万星，MIT。README 的定位是「focused on making agents that learn, not just remember」。

架构（据官方 README）：

- 记忆存在 bank 里，分四类：世界事实（world facts）、经历（experiences，Agent 自身的经历）、观察（observations，从多条记忆巩固出的、带证据引用的信念）、心智模型（mental models，对某个问题的常驻答案，后台持续重写）。
- 三个操作：retain 用 LLM 抽事实、时间、实体和关系并规范化；recall 并行跑四路检索（语义、BM25、实体/时间/因果图、时间范围过滤），再用 RRF 融合 + cross-encoder 重排，按 token 上限裁剪；reflect 对已有记忆做深度推理，形成新联系。
- 后台把零散事实巩固成 observation，每条都保留原文引用；还有可投影成 Markdown 的「知识页」。
- Docker 一键起服务，内置 Postgres，也支持外部 Postgres；支持 25+ 模型提供方，含 Ollama 等本地模型。

亮点：区分「世界」与「自我经历」，把反思和巩固做成一等操作；observation 带证据，可追溯。

适用场景：需要从经验中改进的长期 Agent，如项目经理 Agent、销售外联 Agent、支持 Agent。

外部评价：[@ZenithYeAI](https://x.com/ZenithYeAI/status/2103902826917138658) 拆解了它的四类记忆与四路检索。[@nicoloboschi](https://x.com/nicoloboschi/status/2032389907432271908) 称其基准优于 Google 的 Always On Agent Memory Layer——此人疑为项目相关方，属利益相关自述。README 自称在 LongMemEval 上达到 SOTA，并称结果被弗吉尼亚理工 Sanghani 中心和《华盛顿邮报》研究合作者复现；仍属自报，复现报告未经本文核读。[@SteveMacNI](https://x.com/SteveMacNI/status/2113773533490717096) 则反馈在多 Agent 场景下与 OpenViking 一起试用很痛苦，后来改用 Honcho。

许可与定价：MIT；Hindsight Cloud 按用量计费、有免费额度（[vectorize.io/pricing](https://vectorize.io/pricing)）。

### SuperMemory：记忆 + RAG + 画像打包

是什么：把用户画像、记忆和 RAG 合成一个 API 的引擎，[supermemoryai/supermemory](https://github.com/supermemoryai/supermemory)，3.1 万星，仓库 MIT。

架构：自动维护用户画像，处理矛盾事实，可以通过代理替换 base URL 的方式「无感」接入。

亮点：drop-in，产品团队一天能接上。

适用场景：想同时拿到「记住用户」和「检索文档」、又不想自己拼管线的团队。

外部评价：第三方对比（[aiagentmemory.org](https://aiagentmemory.org/articles/llm-memory-comparison/)）指出，本地自托管 server 据称以二进制形式提供，核心服务端不在公开仓里。本文未能独立核实这一点，选它做「完全开源自托管」前请自行确认。

许可与定价：仓库 MIT；托管服务按官网。

### Memori：从「Agent 做了什么」里抽记忆

是什么：[MemoriLabs/Memori](https://github.com/MemoriLabs/Memori)（原 GibsonAI），1.7 万星。GitHub API 显示许可为 NOASSERTION，LICENSE 文件实为 Apache-2.0。口号是「Memory from what agents do, not just what they say」。

架构（据 README）：包装你的 LLM 客户端（Memori().llm.register(client)），用 attribution(entity_id, process_id) 标记用户和流程，后台自动持久化并召回；除对话外，也捕获工具调用、决策和结果。默认走 Memori Cloud；BYODB 模式可接你自己的数据库。提供 OpenClaw、Hermes Agent 插件。

亮点：零侵入（不改提示词）；结构化记忆进 SQL，数据在自己手里。

适用场景：已有数据库栈、希望记忆可被 SQL 查询和审计的团队。

外部评价：README 称在 LoCoMo 上 87% 准确率、平均每次查询 721 token，并称优于 Zep、LangMem、Mem0（附 [arXiv 2603.19935](https://arxiv.org/abs/2603.19935)）——典型的自报横比，裁判与设置不同，参考价值有限。

许可与定价：Apache-2.0；Cloud 需 API key，价格以官网为准。

抽取层侧栏

Memobase（2944 星）：用户画像 + 事件时间线，适合做 C 端画像。SimpleMem（3859 星）：研究向，主打低成本的终身记忆。两者星标不高，供参考。

## ② 写路径专用模型：把「写什么」交给一个训练过的模型

抽取层的通病是：用通用大模型临时判断「这句话值不值得记、和旧记忆冲不冲突」，既贵又不稳。腾讯混元给出的答案是专门训练一个写记忆的模型。

### Hy-Memory 2.0 + MemHub

是什么：腾讯混元开源的「双系统认知记忆引擎」和 Python SDK（hy-memory），[Tencent-Hunyuan/Hy-Memory](https://github.com/Tencent-Hunyuan/Hy-Memory)，1902 星。API 显示 NOASSERTION，LICENSE 文件确认 Apache-2.0，且明确覆盖代码、参数与权重。

架构（据 README 与论文列表）：

- 写模型：[Hy-Memory-30B-A3B](https://huggingface.co/tencent/Hy-Memory-30B-A3B)，30B 总参、约 3B 激活的 MoE，用「归因强化学习」专门训练长期记忆抽取与冲突调和（[技术报告 arXiv 2610.22196](https://arxiv.org/abs/2610.22196)）；已开源 FP8 与 GGUF 量化版。
- SDK：Chat / Work / Code 三类场景各有专用管线。Chat 记忆来自 EMNLP 2026 论文的「双过程」架构，把个人记忆组织成 8 层（原始对话、原子事实、摘要、图式等）；Code 记忆来自 CMB 基准论文，用「两层 + 版本演化 diff 链」同时保留工程经验和代码修订轨迹。
- 检索返回 profile / normal / proactive 三个通道。
- MemHub（同仓 memhub/）：桌面应用 + CLI，在 Cursor、Codex 等多个编程工具之间同步记忆。

亮点：这是目前开源里唯一把写路径单独做成模型的方案；只需一个 OpenAI 兼容的 LLM 和 embedding 端点即可跑 SDK。

适用场景：记忆写入量大、通用模型抽取成本或准确率成为瓶颈；希望本地部署写模型。

外部评价：官方 [@TencentHunyuan](https://x.com/TencentHunyuan/status/2111027329816465435) 发布帖 1314 赞、1128 收藏（官方，利益相关）；[@NFT_Chen](https://x.com/NFT_Chen/status/2111034063582802276)、[@shao__meng](https://x.com/shao__meng/status/2111082839068246301) 有中文解读。星标低是因为 2026 年 10 月才开源，热度集中在 Hugging Face。

许可与定价：Apache-2.0，自托管免费；官网 [memory.hunyuan.tencent.com](https://memory.hunyuan.tencent.com/)。

## ③ 时序与知识图：让记忆知道「什么时候什么为真」

### Graphiti / Zep：双时间轴上下文图

是什么：Graphiti 是开源的时序上下文图框架，[getzep/graphiti](https://github.com/getzep/graphiti)，3.2 万星，Apache-2.0；Zep 是基于它的商业上下文平台。

架构：三层子图——情节（Episode，原始事件）、语义实体（Entity）、社区（Community）。每条事实边带 valid_from / valid_to 和来源；新事实到来时把旧边标记为失效而不是删除（bi-temporal）。检索并发 BM25、向量和图遍历，再用 RRF / MMR 融合，可选 rerank（[论文 arXiv 2501.13956](https://arxiv.org/html/2501.13956)）。

亮点：能回答「上个月这个客户用的是什么版本」这类时间旅行查询；有来源可追溯。事实会过期、需要时间旅行查询，正是这种设计瞄准的问题。

适用场景：客服、CRM、企业知识这类事实频繁变化、需要审计历史的场景。

外部评价：研究叙事强，社区对比常说「图更强，但搭建和运维不如 Mem0 轻」（如 [calvinku.dev 的对比](https://www.calvinku.dev/blog/from-beta-to-battle-tested-picking-between-letta-mem0-and-zep)）。需要自备图数据库。

许可与定价：Graphiti Apache-2.0；Zep 托管按 [getzep.com/pricing](https://www.getzep.com/pricing/)。

### Cognee：把异构数据变成图 + 向量

是什么：开源记忆引擎，[topoteretes/cognee](https://github.com/topoteretes/cognee)，3.3 万星，Apache-2.0。文档、代码、对话进来，出图谱 + 向量 + 关系；API 是 remember / recall / improve / forget。

架构：抽取实体与关系建图，支持本体（ontology）校验，可接本地小模型和多种图库。

亮点：横跨文档 RAG 和 Agent 记忆；遗忘是显式 API。

适用场景：要把一堆异构资料建成可推理的知识图，再给 Agent 回忆用。

外部评价：[@mycomradio](https://x.com/mycomradio/status/2080481583677460703) 介绍 v1.4.0 的数据集级概览索引与多种检索模式（帖中的用户数与客户名本文未核）。[@g_korland](https://x.com/g_korland/status/2081727517027704936) 推荐用 FalkorDB 做底座——他是 FalkorDB CEO，利益相关。另有第三方称部分生产能力有授权限制，本文未在官方条款中核实。

许可与定价：Apache-2.0；托管版见官网。

图谱侧栏

MIRIX（3456 星）：六类记忆（核心、情节、语义、程序、资源、保险库），支持多模态。A-MEM（1212 星）：卡片盒笔记法，新笔记会改写相关旧笔记，自组织。Memary（2663 星）：知识图 + 记忆流。都是设计上有意思的研究型项目。

## ④ OS 式与自编辑：把记忆当成操作系统的内存管理

这一派的隐喻来自 MemGPT：上下文窗口是内存，外部存储是磁盘，Agent（或调度器）负责换入换出。区别在于谁来管、管成什么形状。

### Letta：记忆就是 Agent 的身份

是什么：原 MemGPT 团队的有状态 Agent 框架，[letta-ai/letta](https://github.com/letta-ai/letta)，2.5 万星，Apache-2.0。

架构：2026 年的核心是 MemFS（[文档](https://docs.letta.com/concepts/memfs/index.md)）——记忆存在 git 仓库里，投影成本地文件系统；system/ 目录常驻 system prompt，其余文件按需展开（progressive disclosure）。Agent 不再调用专门的「改记忆工具」写数据库，而是用 bash 和文件工具直接改自己的记忆文件。后台还有「dreaming」式的巩固。

亮点：OS 隐喻最彻底；记忆可版本化、可 diff、人可审阅。

适用场景：长期运行、需要自己维护身份与技能的自主 Agent。

外部评价：社区友好、概念深；第三方生产对比普遍认为它作为「记忆 API」偏重、学习曲线陡（[calvinku.dev](https://www.calvinku.dev/blog/from-beta-to-battle-tested-picking-between-letta-mem0-and-zep)）。它更像一个 Agent 运行时，而不是一个可以随手挂上的记忆库。

许可与定价：Apache-2.0；托管版见 [Letta 定价页](https://docs.letta.com/pricing/index.md)。

### MemOS：记忆操作系统 + 记忆立方体

是什么：记忆张量团队的「LLM 与 Agent 记忆操作系统」，[MemTensor/MemOS](https://github.com/MemTensor/MemOS)，1.2 万星，Apache-2.0（README 与 LICENSE 均确认）。当前版本 MemOS 2.0「星尘」。

架构（据 README）：

- 统一记忆 API：增、查、改、删，记忆组织成图，设计上可检查、可编辑，而不是黑盒向量库。
- Multi-Cube：把多个知识库组织成可组合的「记忆立方体」，在用户、项目、Agent 之间做隔离、受控共享和动态组合。
- MemScheduler 异步摄入，面向高并发；支持用自然语言反馈修正、补充、替换记忆。
- 多模态：文本、图片、工具轨迹、人设一起存取。
- 部署三选一：托管云、自托管（Neo4j + Qdrant）、本地插件（SQLite）。本地插件把记忆分为 L1 轨迹、L2 策略、L3 世界模型，并沉淀成技能。

亮点：把「知识库」和「记忆」统一成可组合的 Cube；对 OpenClaw、Hermes、DeepSeek Harness 都有官方插件。

适用场景：要同时管理多个用户、多个项目的记忆与知识库，并需要受控共享的团队。

外部评价：README 自报 LoCoMo 88.83、LongMemEval 89.20，并称在其自建的 OmniMemEval 上领先 14 款商业记忆产品，还称让 OpenClaw 五项任务平均完成率从 36.63% 升到 50.87%。评测框架由项目方自建，属自报；Raw-RAG 论文的对比对象里也包括 MemOS 族系统，结论相反。

许可与定价：Apache-2.0；云服务按官网。

### EverOS（EverMemOS）：Markdown 是唯一真相源

是什么：EverMind 的本地优先记忆运行时，[EverMind-AI/EverOS](https://github.com/EverMind-AI/EverOS)，1.4 万星，Apache-2.0。评测和宣传里常用旧名 EverMemOS，仓库名是 EverOS。

架构（据 README）：

- 对话、文件、Agent 轨迹都存成可读的 Markdown，这是唯一真相源；直接编辑 .md，监听器会同步索引。
- 本地三件套：Markdown + SQLite + LanceDB，不需要 MongoDB、Elasticsearch、Redis。
- 用户轨道（情节、画像）和 Agent 轨道（案例、技能）分开。
- 按 user_id、agent_id、app_id、project_id、session_id 正交检索。
- 离线「反思」：在会话之间合并情节簇，精炼画像和技能。
- 集成 DeepSeek Harness、Hermes、OpenClaw、Dify。

亮点：可 diff、可 git 版本化的记忆，对个人开发者极友好；本地栈极轻。

适用场景：个人或小团队，在多个编程助手、应用和设备之间共用一份可移植记忆。

外部评价：[@tec_aryan](https://x.com/tec_aryan/status/2067601318592827823) 介绍了 1.0 的 Markdown + SQLite/LanceDB 设计。基准存疑：[@0xwolverines](https://x.com/0xwolverines/status/2112502393648697527) 指出其云服务宣称的 93% 只比「把全部对话塞进上下文」的基线高约 1 个百分点。这恰好说明：比较记忆系统，一定要看它和全上下文基线的差距，而不是绝对分。

许可与定价：Apache-2.0；云服务按官网。

### TencentDB Agent Memory：给 Agent 团队的记忆中枢

是什么：腾讯云开源的团队记忆系统，[TencentCloud/TencentDB-Agent-Memory](https://github.com/TencentCloud/TencentDB-Agent-Memory)，3.0 万星。API 显示 NOASSERTION，LICENSE 文件确认为 MIT。

架构（据 README）：

- 三个服务：memory-core、memory-hub、proxy。接入方式是代理：把 Agent 的 base URL 指向 Proxy，不需要插件、hook 或 MCP，支持 Claude Code、Codex、CodeBuddy、Hermes、OpenClaw、DeepSeek Harness 等。
- Chat Memory 分四层逐级蒸馏：L0 对话 → L1 原子事实 → L2 场景 → L3 人设。X 上流传的「4 层渐进管道」指的就是这个。
- Skill 库：从对话和工具调用中抽取技能，技能带版本、资源文件、触发边界、执行步骤和验证规则。
- Wiki + CodeGraph：把文档变成带链接图的结构化页面（README 注明受 Karpathy LLM 知识库启发），把代码变成符号、调用关系和影响路径索引。
- 团队面板：private / team / restricted 三级可见性，按用户、角色、Agent 设 ACL；个人技能默认私有，审核后才共享。
- 存储后端可选 MongoDB（实验性，默认关闭）。

亮点：开源里少见的「团队级」记忆治理：所有权、版本、审核、可见性都有；冷启动可导入已有文档、代码库和历史会话。

适用场景：一人公司或小团队用多个 Agent 协作，希望经验能在 Agent 和成员之间流转。

外部评价：[@so_sthbryan](https://x.com/so_sthbryan/status/2085861292687138918) 称其为本地运行、零外部 API 的四层管道。需要说明的是，README 的安装步骤要求填写两组 LLM 参数（记忆组和代理组），「零外部 API」更准确的理解是「可以全部指向本地模型」。

许可与定价：MIT，自托管免费。

OS 式侧栏

MemoryOS（BAI-LAB，1616 星）：短、中、长期三层，带更新、检索、生成模块，学术向，结构清晰，适合读代码学设计。

## ⑤ 文件、文件系统与上下文数据库：记忆就是一个文件夹

2026 年最有意思的变化：越来越多的项目放弃「黑盒向量库」，把记忆变成人和 Agent 都能直接读写的文件。起点很朴素——Claude Code 的 CLAUDE.md、Cursor 的 rules、Karpathy 提出的「LLM wiki」（让模型自己维护一个 Markdown 知识库）。终点则是 OpenViking 这样的「上下文数据库」。

### OpenViking：一个文件系统装下 Agent 知道的一切

是什么：火山引擎 Viking 团队开源的「自进化上下文数据库」，[volcengine/OpenViking](https://github.com/volcengine/OpenViking)，4.1 万星，AGPL-3.0，2026 年 1 月开源。口号是「one filesystem for everything an agent knows」。

架构（据官方 README 与 [docs.openviking.ai](https://docs.openviking.ai/)）：

- 统一 URI 命名空间：viking://{scope}/{path}，公开 scope 有 resources（文档、代码）、user（用户记忆）、agent（Agent 记忆与技能）。Agent 用 ls、tree、read、write、grep、find、search 像逛文件系统一样导航。
- 三类上下文同居：Resources、Memories、Skills 各有 URI，可浏览、可检索。这是它和纯记忆库最大的不同：记忆、文档 RAG、技能在一个系统里。
- L0 / L1 / L2 分层加载：每个目录有两个旁路文件——L0 .abstract.md（默认约 256 字，用于向量快筛）、L1 .overview.md（约 4k，用于导航和重排）、L2 是原文，按需才读。
- 双层存储：RAGFS 存内容，向量索引存 URI、向量与元数据。检索流程是「意图分析 → 在目录范围内向量召回 → 可选 rerank」，按目录范围检索，而不是扁平扫全库。
- 会话提交：commit() 同步归档消息，异步生成摘要并抽取长期记忆（抽取循环 → MemoryUpdater 合并去重 → 写回），并输出 memory_diff.json 供审计。

亮点：先摘要后原文，天然省 token；目录即权限边界，范围检索更准；记忆变更有 diff 可审计；有 Studio 可视化浏览，插件覆盖 Claude Code、Codex、Cursor、TRAE、OpenCode。

适用场景：Agent 需要同时用到文档、个人记忆和技能，并且希望这一切可浏览、可审计；或者想给多个编程助手配同一个上下文后端。

外部评价：[@stometaverse](https://x.com/stometaverse/status/2108163928866058564) 写了自部署长文；[@ancapdp](https://x.com/ancapdp/status/2107892081779728780) 在对比后选了本地 OpenViking；[@SteveMacNI](https://x.com/SteveMacNI/status/2113773533490717096) 则反馈多 Agent 场景下与 Hindsight 一起用不顺，最终换成 Honcho。官方博客自报接入后 OpenClaw、Hermes、Claude Code 在 LoCoMo 上约 80–83%，属自报。不少英文热门榜单几乎都漏了它，这也是只看单一语种榜单选型的风险。

许可与定价：AGPL-3.0——如果你修改后以网络服务形式提供，必须开源修改；闭源 SaaS 集成前请过一遍法务。可自托管 openviking-server，火山引擎也有托管服务。

OpenViking 侧栏：MineContext

同为火山引擎开源的 [MineContext](https://github.com/volcengine/MineContext)（5542 星，Apache-2.0）是「主动式上下文伙伴」，偏向主动收集和整理用户上下文的桌面助手，而不是记忆库本身。

### GBrain：Garry Tan 的个人与公司大脑

是什么：YC 总裁 Garry Tan 开源的记忆层，[garrytan/gbrain](https://github.com/garrytan/gbrain)，3.1 万星，MIT。README 第一句：「Give the agent you already use a memory you control.」

架构（据 README）：存储显式事实及其来源，支持更正和撤回；同一份记忆供多个 Agent 共用。在关键词与语义检索之外，提供两个可选层：综合层（直接给出带引用的答案，而不是返回 10 个片段）和类型化知识图（本地写页面时不调 LLM 也能抽取引用关系）。远程客户端受来源与操作授权、可见性过滤约束；可通过 MCP 在 Tailscale 上暴露给云端 Agent；一个 24/7 后台守护进程负责摄入、丰富和巩固。

亮点：作者自己的生产规模——README 称支撑其 OpenClaw 与 Hermes 部署，有 155,795 页、24,589 人、5,340 家公司（作者自述）；「先给答案再给出处」的检索体验。

适用场景：重度个人知识管理、投资人或销售这类以人和公司为中心的关系网络、小公司共享大脑。

外部评价：在 X 上热度极高，很大程度来自作者本人的影响力。README 自己也提醒：Markdown 导出不等于完整数据库备份，配置的云端 embedding、重排、抽取服务会接收文本。

许可与定价：MIT，可免费自托管；gbrain.io 为可选付费托管。

### memU：个人记忆，存成 Wiki

是什么：[NevaMind-AI/memU](https://github.com/NevaMind-AI/memU)，1.5 万星。API 显示 NOASSERTION，仓库 LICENSE.txt 与 README 标注为 Apache-2.0。

架构（据 README）：跨会话、跨 Agent、跨设备共享的「LLM wiki」。亮点是自动技能抽取：宿主适配器读取新会话（含工具调用）→ 切成独立任务 → 由 Agent 自己决定不动、修补已有技能还是新建技能 → 写成可读的 Markdown 技能 → 提交并索引 → 下次相似任务召回。README 特别说明 MemoryService 本身不调用任何 LLM，判断和综合全部留在 Agent 里。

亮点：把「程序记忆」做成可读技能文件；记忆服务本身零 LLM 成本。

适用场景：Codex、Claude Code、Cursor、OpenClaw 等多个编程助手的重度用户，想把踩过的坑沉淀成技能。

外部评价：常见于各类开源记忆推荐帖（例如 [@Lummox_eth](https://x.com/Lummox_eth/status/2104218875810185287)）。README 的兼容矩阵很诚实：ChatGPT 普通聊天和 Claude 网页聊天不支持，部分模型可能拒绝执行安装步骤。

许可与定价：Apache-2.0；托管版 memu.so 称免费，自托管需自备 embedding key。

### Memvid：整份记忆就是一个文件

是什么：[memvid/memvid](https://github.com/memvid/memvid)，1.7 万星，Apache-2.0。「单文件记忆层，不需要数据库。」

架构（据 README）：把数据、embedding、检索结构和元数据打包成一个 .mv2 文件。设计借鉴视频编码：记忆是只追加、不可变的 Smart Frame 序列，每帧带时间戳和校验和；因此能查询过去任一时刻的记忆状态、回放、分支，崩溃安全。

亮点：可移植、可离线、自带时间旅行；分发一份记忆就像分发一个文件。

适用场景：边缘设备、离线 Agent、需要把一份记忆打包交给别人的场景。

外部评价：README 宣称 LoCoMo 上「+35% SOTA」、P50 延迟 0.025ms 等，均为自报，且「比行业平均高 76%」这种表述缺少可比基线，读者应谨慎。

许可与定价：Apache-2.0；另有官网沙盒。

### 不需要任何项目的那一层：CLAUDE.md 与 LLM wiki

在上面所有项目之下，有一层很多人跳过的地板：一个 Markdown 文件就是记忆。Claude Code 的 CLAUDE.md、Cursor 的 rules 文件，以及 Karpathy 描述的「让 LLM 维护一个 wiki」，本质都是由人或 Agent 编辑的程序记忆加少量语义记忆，由 harness 在会话开始时整段加载。

它的上限很清楚：几百条事实以内好用，超过就塞不进上下文；没有自动捕获，没有跨工具同步，没有冲突处理。但它是最透明、最便宜、最不会出「静默改写」事故的方案。本文的建议是：先用它跑通，再按痛点升级。

文件派侧栏

Basic Memory（4432 星，AGPL-3.0）：本地 Markdown 知识图，通过 MCP 给 Claude 等读写。LongMemory（原 OpenMemory，4557 星，Apache-2.0）：不可变内容 + 来源 + 时间真相，SQLite + MCP。mcp-neo4j（989 星，MIT）：带记忆服务器的 Neo4j MCP。

## ⑥ Coding Agent 跨工具记忆：2026 年星标涨得最快的一类

编程助手是记忆需求最刚性的场景：架构说明、失败过的方案、仓库约定，每开一个新会话都要重讲一遍；换一个工具（Claude Code → Codex → Cursor）更是从零开始。这一类项目的星标增速远超通用记忆层。

### claude-mem：会话自动压缩，下次自动注入

是什么：「为 Claude Code 打造的持久记忆压缩系统」，[thedotmack/claude-mem](https://github.com/thedotmack/claude-mem)，10.8 万星，Apache-2.0。

架构（据 README）：通过 harness 的生命周期 hook 自动捕获工具调用观察，生成语义摘要，在之后的会话里自动注入；没有 hook 的宿主（README 举例 Grok Bot）则改为监听聊天日志文件。检索采用渐进披露，分层加载并显示 token 成本；用隐私标签排除敏感内容；每条观察有 ID，可引用。一个本地 worker 服务承担捕获与召回，另有 Web 查看器。现在已扩展到 Codex、OpenClaw、Pi、DeepSeek Harness 等。

亮点：零配置，装完重启 Claude Code，上次的上下文就出现在新会话里。

适用场景：Claude Code 重度用户；想要「开箱即用」的编程会话记忆。

外部评价：[@FielxZhu](https://x.com/FielxZhu/status/2116551769300099420) 称其登上 GitHub 日榜第一。[@thelazyaicoder](https://x.com/thelazyaicoder/status/2107678309656223960) 提醒：安装器默认使用托管记忆，需显式传 --provider 才走本地。这一点 README 也写明了：默认是 CMEM Pro 托管，本地观察器需 --provider host 主动开启，CI 和非交互环境会跳过登录。注意：10 万星反映的是编程工具的病毒式传播，不等于它是功能最深的通用记忆库。

许可与定价：Apache-2.0；托管同步 cmem.ai 按官网。

### ai-memory：换工具不换记忆，带着会话走

是什么：[akitaonrails/ai-memory](https://github.com/akitaonrails/ai-memory)，1.5 万星，MIT。场景描述很直接：Claude Code 做到一半退出，在同一目录打开 Codex，继续干活，不用重讲架构、失败方案和待解问题。

架构（据 README）：

- 20 多个 harness（Claude Code、Codex、Cursor、Gemini CLI、OpenCode、Grok、Devin、Kimi、Kiro 等）写入同一份记忆。
- 交接（handoff）是类型化协议：每个交接有所有者，只能被认领一次。
- ai-memory run codex 可以把上一个工具的原生历史做成本地临时投影交给下一个工具；远程服务器只收到 harness 和会话标识，不收原文。
- 跨项目的个人工作习惯画像（包管理器、测试布局等），作为仓库规则文件之下的默认层。
- 记忆服务器自己部署；团队共享按项目，个人交接保持私有；多用户认证、署名和审计日志都内置，不是付费功能。
- 真相源是 git 管理的 Markdown wiki，可以 grep、可以用 Obsidian 打开。

亮点：把「工具之间交接」做成协议，而不是靠摘要碰运气；隐私边界讲得清楚。

适用场景：在多个编程助手之间切换的个人开发者，以及共享一台记忆服务器的小团队。

外部评价：[@FengIves](https://x.com/FengIves/status/2112126063115706614) 有中文推荐。

许可与定价：MIT，自托管免费。

Coding 记忆侧栏

Beacon（[Asymptote-Labs/agent-beacon](https://github.com/Asymptote-Labs/agent-beacon)，2980 星，MIT）：跨 Claude Code、Cursor、Codex、OpenCode 等 20+ harness 捕获会话历史，把有用的流程、纠错和调试模式沉淀成可复用知识，本地优先。中文介绍见 [@sanyanzhumo](https://x.com/sanyanzhumo/status/2112810754357297522)。另有 [@daksh_jaitly](https://x.com/daksh_jaitly/status/2115412503966699860) 的对比测试称 Beacon 0/24、mex 24/24——发帖方为竞品相关，未独立复现，只能当作争议。MemHub：Hy-Memory 的桌面应用层（见 ②），在多个编程工具之间本地同步记忆。

## ⑦ 身份建模：记住「这个人是谁」，而不只是「他说过什么」

### Honcho：以 Peer 为中心的推理式记忆

是什么：Plastic Labs 的记忆服务，[plastic-labs/honcho](https://github.com/plastic-labs/honcho)，7870 星，AGPL-3.0（README 与 LICENSE 确认）。

架构（据 README）：

- 数据模型：Workspace 下有 Peer 和 Scope；Peer 参与 Session，消息挂在 Session 上。用户、Agent、群组、项目都是 Peer。
- 两个服务：Storage（同步 API，存工作区、Peer、会话、消息）和 Insights（后台推理、结论、表征、摘要、对话端点）。
- 循环是「存储 → 后台推理更新每个 Peer 的表征 → 查询 → 注入」。可以直接问「这个用户对哪种学习方式反应最好」，Honcho 用推理后的结论回答。
- 可配置多 Peer 视角：建模 A 对 B 知道什么——内部集合按「观察者 / 被观察者」配对存储。
- FastAPI 服务，Postgres + pgvector；可用托管 api.honcho.dev，也可 honcho start 本地运行。

亮点：抽取的是结论而不是片段；多方视角建模在开源里几乎独一份，适合群聊和多 Agent 场景。

适用场景：陪伴、教育、教练类产品；多用户、多 Agent 的群体对话。

外部评价：[@SteveMacNI](https://x.com/SteveMacNI/status/2113773533490717096) 在多 Agent 场景下试过 OpenViking 和 Hindsight 后转向 Honcho。README 自称「定义了 Agent 记忆的帕累托前沿」并附评测页（自报）。

许可与定价：AGPL-3.0，商业闭源集成需注意；托管版注册后每个组织一个独立实例，价格以官网为准。

### Second Me：训练一个「AI 版的你」

是什么：Mindverse 的开源个人 AI 身份原型，[mindverse/Second-Me](https://github.com/mindverse/Second-Me)，1.6 万星，Apache-2.0。

架构（据 README）：用你自己的记忆在本地训练个人模型，方法是分层记忆建模（HMM）和 Me-Alignment 算法（[论文 arXiv 2503.08102](https://arxiv.org/abs/2503.08102)）；Docker 部署，README 给出了内存与可训模型规模的参考表；训练好的「第二个我」可以在授权后接入去中心化网络，代表你和其他人或应用交互。

亮点：记忆的终点不是检索，而是写进模型参数；数据和训练都在本地。

适用场景：个人数字分身、角色扮演、隐私敏感的个人记忆实验。

外部评价：路线激进，硬件门槛明显；README 的路线图停在 2025 年 5 月，活跃度建议入场前自查。

许可与定价：Apache-2.0。

### 运维与许可风险

- 最轻：Memvid（一个文件）、EverOS（三件套）、CLAUDE.md（零依赖）。
- 中等：Mem0、Hindsight、Memori、ai-memory（一个服务 + 一个库）。
- 较重：Graphiti（图数据库）、MemOS 服务端（Neo4j + Qdrant）、TencentDB AM（三个服务）、OpenViking（服务 + 向量索引）。
- AGPL 三家：OpenViking、Honcho、Basic Memory。改了代码并以网络服务提供就要开源修改，闭源 SaaS 集成前务必评估。

## 坑与反模式：收藏这一节就够了

> 坑 1：迷信基准分。 LoCoMo、LongMemEval 的分数几乎全是自报，裁判模型、提示词、子集都不同。Redis 用统一协议复测时直言部分厂商分数无法复现；EverOS 的 93% 只比全上下文基线高约 1 分。看分数，先看它和「全塞上下文」「朴素 RAG」两条基线的差距。

坑 2：复杂不等于更好。 Raw-RAG 论文显示「原始对话 + 稠密检索 + rerank」能打赢多款复杂记忆系统。上复杂写路径之前，先用朴素方案做一条基线。

坑 3：拿知识库当用户记忆，或反过来。 把产品手册塞进 Mem0，或用 GraphRAG 存用户偏好，都是用错了工具。按开头那张边界表拆开。

坑 4：静默更新。 写时合并如果没有来源和变更记录，记错了你永远不知道是哪一轮写错的。选型时优先看有没有 provenance、diff 或 git 历史（Graphiti、OpenViking、Letta、ai-memory、EverOS 都有）。

坑 5：租户串记忆。 user_id 用错一个就是事故。Mastra 文档专门警告线程所有者创建后不可更改、不要跨所有者复用线程 ID；作用域信息必须来自服务端，不能信任客户端传入。

坑 6：只写不忘。 没有衰减、过期和删除，记忆会越来越像垃圾场。确认系统有显式遗忘（Cognee 的 forget）、TTL（Redis）或巩固机制（Hindsight、CrewAI、EverOS）。

坑 7：忽略抽取成本。 每条消息都调一次 LLM 抽取，价格页通常不会写。[@sermakarevich 的横评](https://x.com/sermakarevich/status/2115087554877776113) 专门把「价格页没算的抽取 token」算了进去。这也是 Hy-Memory 训练专用小激活模型、memU 让记忆服务零 LLM 调用的动机。

坑 8：只看单一语种热门榜。 OpenViking 4 万星、Hy-Memory 刚开源，不少英文热门榜几乎都没收。选型时中英文都要扫。

坑 9：把开源 SDK 当成托管全部能力。 图记忆、仪表盘、团队协作，很多只在托管版。

- 离线和边缘：Memvid 或 EverOS。

## 结语：记忆是策略问题，不是选库问题

把 40 多个项目摊开，会发现真正的差别不在向量库、不在 embedding 模型，而在三个决定：谁来写、冲突怎么办、错了能不能追溯。2026 年的几条主线也很清楚：记忆在变回文件（Letta、EverOS、OpenViking、ai-memory），程序记忆在变成技能（memU、TencentDB、Beacon），写路径开始有专用模型（Hy-Memory），而朴素基线一再提醒大家别过度设计（Raw-RAG）。

收藏这篇，下次选型时只需要回来看三样东西：写路径光谱图、冲突处理表、选型决策树。如果你在生产里踩过本文没写到的坑，欢迎在评论区补充。
