Chrome 官方案例：Policybazaar 用 Agent 将复杂前端开发验证从 4 天缩至数小时，性能审计工作量减少 92%

Coding Agent 能写前端代码，不代表它知道页面实际渲染得怎么样。Chrome 官方介绍的 Policybazaar 案例，补上的正是这一步：用 Modern Web Guidance 约束代码写法，再用 Chrome DevTools for agents 检查真实页面，让生成、检查和修复接起来。

这个案例包含两条不同的工作流：Policybazaar 用 Agent 做上线前性能审计；关联品牌 Pensionbazaar 则把设计稿、代码生成和浏览器验证串成闭环。

# 一边写页面一边在浏览器里验证

Pensionbazaar 在 Claude Code 中通过 Figma MCP 读取设计稿，生成代码后启动干净的浏览器，检查视觉一致性、响应式布局、控制台报错和性能，发现问题再修改。

其中，Modern Web Guidance 提供现代 Web 开发规则，并以 Baseline 兼容性范围约束实现。例如，同一张图片不应同时设置高加载优先级和懒加载；首屏关键图片与普通图片也不能一视同仁。

最终交给 QA 的不只是代码，还包括设计稿对比、多尺寸截图、性能诊断和交互检查结果。工程师审阅仍然保留，但许多明显问题已在此前被发现并修正。

# 性能审计从人工逐页检查，变成统一执行

Policybazaar 寿险团队维护约 30 个落地页及营销变体，每天承接约 20 万至 30 万次访问。过去工程师需要手工收集性能数据、定位瓶颈，测试覆盖不够稳定。

新流程中，工程师在 Kiro 内对预发页面分别发起移动端和桌面端审计。Agent 执行 Lighthouse 和性能追踪，同时获取 Chrome 用户体验报告（CrUX）的真实用户数据，对照分析后给出修复优先级。

一次审计发现，页面加载时串行触发的非关键 API 正在与关键渲染争抢资源，团队因此能在上线前修复。这里 Agent 负责检查和诊断，修复仍由工程师完成。

# 改善最明显的是验证效率

在团队的实践中，Agent 完成 12 次性能审计所需的时间，约相当于工程师手工完成一次，人工审计工作量下降约 92%，活动页性能测试覆盖率达到 100%。

Pensionbazaar 新页面从代码到完成验证，由约四天缩短至数小时；因界面与设计线框不符而提出的 UI 缺陷减少了 90% 以上。这些数字衡量的是审计、验证和交付效率，并不是线上核心网页指标提升了相同比例。
