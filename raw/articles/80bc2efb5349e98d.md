# 先真正运行，再判断完成

团队把启动和冒烟检查写成 verify Skill，让 Claude 在提交前执行。检查失败后尝试修复，三轮仍失败则交给人。

验证也不是每次机械执行所有检查。一份 39 项可靠性清单根据代码改动触发，通常只检查相关的 3—10 项。例如修改会话存储，就要确认旧记录仍能通过 --resume 安全恢复。检查由代码所有者编写，让具体的工程经验成为可重复执行的步骤。

# 改代码，不能顺便改掉评判标准

Claude Code 团队最重要的一条原则是：如果一项改动能修改评判自己的检查，这套检查就失效了。

因此，代码审查规则 REVIEW.md 从基础分支或默认分支读取，而不是采用当前拉取请求里可能被修改的版本；审查也针对固定提交，避免代码变化后结论仍被沿用。

每次提交还会记录验证方式，包括明确标注“未验证”。系统可以拦截没有运行审查或验证的提交，但同一会话连续拦截两次后会放行，以免陷入死循环。这说明它是带人工兜底的工程机制，不是绝对安全保证。

# 验证器本身，也要接受验证

团队用回滚记录、维护者拒绝的改动，以及规模相近的正常改动评估审查效果，并恢复当时的仓库状态。只有准确指出实际缺陷的发现才计分，不能靠泛泛提醒获得好成绩。

漏检也不会直接变成新规则：同类问题至少要在两个拉取请求中出现、能从代码差异中识别，再经三个 Agent 尝试找出反例，最后由人批准。这样既积累经验，也避免规则越来越多、误报越来越重。
