# 2026硅谷AIE大会:Flask 作者自查一年会话：每天 120–190 条 prompt 没涨，141 个仓库只有 10–15 个在维护

13 min read

11 月 12 日，AI Engineer Code Summit（AIE CODE 2026）第三天，Armin Ronacher 在主会场讲了《The Software Atelier》（软件工坊）。主持人介绍他的方式是：从创造 Flask 和 Jinja，到探索 AI 时代的软件开发，他影响了一代人怎么做网站。他现在是 Earendil 的 CTO，公司做一个叫 Pi 的编码 agent。

结论先说：他把自己一年的 agent 会话数据翻出来自查，发现机器越来越强，他自己没变。每天发出的 prompt 一年里稳定在 120–190 条；agent 替他干活的时间，从每天几小时涨到四十多小时（并行的 agent 分开算）；他新建了 141 个 git 仓库，真正持续在维护的，始终只有 10–15 个。 所以他的主张是：先别急着建「软件工厂」，先把「工坊」建好，目标不是做更多软件，是做更有野心、质量更高的软件。

这篇只讲这一份自查：数据怎么采、怎么算，查出了什么，以及他从里面得出的做法，包括他在 harness 上正在试的三件事。

### 他是谁

Armin Ronacher，网上叫 mitsuhiko。台上被介绍为 Flask 和 Jinja 的作者，这两个是 Python 世界里最常见的网站开发工具。他现在在 Earendil 做 CTO，公司在做 Pi 编码 agent，他自己的话是：「所以我们在这场比赛里多少有点自己的马。」

他的博客 lucumr.pocoo.org 一直在写。最近几篇是 10 月 6 日的《What is Codemode》和 11 月 9 日的《AI and Irontown》。后一篇他用《幽灵公主》里的铁镇打比方，里面有一句：「我每天都用 AI，也觉得它确实让人更有力量。」又写道：「问题不是会不会有铁，而是我们用它建一座什么样的铁镇。」这就是他这次上台的底色：天天用，用得很深，所以才拿自己当样本去查。

### 一、先说一个比喻：艺术家和 CNC

[/FinanceYF5/article/2121777577903996936/media/2121636476752740353](/FinanceYF5/article/2121777577903996936/media/2121636476752740353)

开场页：先有工坊，再有工厂。来源：AIE CODE 2026 直播

他开场没有讲工厂，讲的是艺术家。一个了不起的艺术家，可以用上最新的技术，从 CNC 机床、3D 打印机到很好用的电动工具，这些会抬高他作品的野心。他说看软件也可以这样看：不是做出多得多的软件，而是做出野心大得多、质量高得多的软件。

接下来整场的内容，都是在回答一个问题：怎样才叫工坊，为什么要先于工厂。

### 二、第一份数据：Pi 的 harness 一年没动，用法却变了

先交代实验条件。Pi 的核心 harness（agent 的外壳）一年没怎么动，工具集和去年 12 月是同一套。所以这一年里 Pi 的变强，来源只有一个：模型变好了。他拿自己的 Pi 会话来画图，而且特意筛过，只留下默认配置的会话，保证不是自己调出来的。

纠正和中断：每换一代模型都在减少

[/FinanceYF5/article/2121777577903996936/media/2121636460948516864](/FinanceYF5/article/2121777577903996936/media/2121636460948516864)

每百条 prompt 里的纠正次数和按 Esc 中断次数，按他切换模型的先后排列。来源：AIE CODE 2026 直播

第一组指标是两个「我插手了多少次」。一个是他要纠正 agent 的总次数，他说用 Jev（一个分类模型）来分析会话，数出每个 session 里他纠正了几次。另一个是他中途打断 agent 的次数。图上把会话按「这个会话里谁调用得最多」归到各个模型名下，再按他切换模型的顺序排开：每百条 prompt 里的纠正，从 GPT-5.3 Codex 的 8.5 降到 Opus 5.5 的 3.9；按 Esc 中断，从 13.1 降到 7.2。他的原话是：用最新模型，他「顶撞」agent 少得多，没有一代是反弹的，一路往下走。

一条 prompt 能让 agent 跑多久：P90 怎么量的

[/FinanceYF5/article/2121777577903996936/media/2121636511691186176](/FinanceYF5/article/2121777577903996936/media/2121636511691186176)

每条 prompt 的 agent 工作分钟数和工具调用次数，取第 90 百分位。来源：AIE CODE 2026 直播

他说这是他最看重的一种分析：看我给 agent 一个任务之后，它连续跑了多久，取第 90 百分位，也就是十次里偏长的那一档。图脚注给了口径：一次「运行」是从他发出 prompt，到他下一条 prompt 之前 agent 的最后一个事件。结果是，去年 12 月用 Opus 4.6，P90 约 2.5 分钟（图上 2.4 分钟，19 次工具调用）；现在最新的模型，P90 是 14 分钟以上（图上 Opus 5.5 为 14 分钟，44 次工具调用）。

他强调一点：这会改变你和 harness 相处的方式，但 Pi 里什么都没改，改变的只是模型。

工具用法：模型自己长出了偏好

[/FinanceYF5/article/2121777577903996936/media/2121636542808825856](/FinanceYF5/article/2121777577903996936/media/2121636542808825856)

同一个 harness 里，不同模型把调用分给 read、edit、write 和各类 bash 的比例。来源：AIE CODE 2026 直播

第三张图是工具调用的占比：read 工具、edit 工具、write 工具，以及按用途拆开的 bash（sed/cat/grep/rg，python/node，git，其他）。他的观察是：现在的 agent 比 harness 提供的其他任何工具都更爱用 Bash。图上最明显的对比是 Opus 5.5：read 工具只占 6%，而 bash 里 sed/cat/grep/rg 这一类占到 43%；前面几个 GPT 模型的 read 工具占 30%–38%。他说得很清楚：harness 的配置一点没变，这是模型自己长出来的行为。

图里还有两处他特意交代了。第一，一小块紫色是 code mode，在慢慢往上爬，他留到最后讲（图脚注说，Opus 5.5 的会话之前 Pi 里还没有 codemode）。第二，Astra 和 Sol 这两个模型，从他的测试看和 Opus 很像，但他的测试集里数据不够，所以没画上去。

过时的技巧：PiAutoResearch

去年大家有过很多「怎么提示机器」「harness 里有什么小技巧」的想法，现在很少还有必要。他自己的例子是 PiAutoResearch：一个让 agent 朝着目标（比如把性能提上去）自己推进的插件，他曾经很喜欢。换上现在最好的模型，他发现这个插件整个都不需要了。

这一段的意思是：模型这一头，每个月都在变；他是拿自己这一头的数字去对照。

### 三、第二份数据：我没变，机器变了

这是整场的核心。他说一年里没变的是：我们还是人，还是受限于最基本的能力。他不想说人是瓶颈，但人是给机器定节奏的那个，而人的注意力，至少对他来说，是一个限制因素。

每天的 prompt 数和 agent 的工作小时数

[/FinanceYF5/article/2121777577903996936/media/2121636509820534784](/FinanceYF5/article/2121777577903996936/media/2121636509820534784)

上：他每天的 prompt 数；下：他每天的 agent 小时数（并行 agent 分开算）。来源：AIE CODE 2026 直播

上面那条线是他自己主动推出去的 prompt 数：一年里每个月有高有低，他的说法是在 120 到 190 条之间来回。图上每个月的数字依次是 126、148、103、117、137、117、182、190、120。

下面的柱子是 agent 替他干活的时间。图脚注给了算法：对每个 session，统计「agent 有活动的分钟数」，间隔不到 3 分钟的空档算作连续，再把同一天里并行的 session 加起来，只算有活动的日子。结果是，从 3 月的 6 小时，到 10 月的 14.4 小时，再到 11 月 1 日至 9 日的 43.7 小时。他自己的说法是，这个数从「少于我一个工作日」涨到了「我工作日的很多倍」，而且「11 月还没过完」，曲线还在往上翘。

也就是：他每天推出去的 prompt 数没变，机器替他干活的时间变成了好几倍。

141 个仓库，只有 10–15 个在维护

[/FinanceYF5/article/2121777577903996936/media/2121636595753517056](/FinanceYF5/article/2121777577903996936/media/2121636595753517056)

折线：累计新建的项目；柱子：当月投入 5 天以上的项目。来源：AIE CODE 2026 直播

第二张图统计的是 git 仓库。折线是他过去一年新建的仓库，累计 141 个（图上从 3 月的 24 个一路到 10 月的 141 个）。柱子是他定的标准：一个月里提交超过 5 天、并且会回头再来的项目，数字是 6、13、9、7、9、11、10、11，一直在 10 到 15 个以内。

他说，开始一个新项目现在容易得不可思议，尤其每次新模型发布，大家都兴奋地去试，从 3D 游戏到各种自动化。但维护一个东西，没有变容易。他还拿这个问题去问了身边一圈朋友，做了一个非正式的小调查，结果是：这是普遍的现象，定期维护某个东西，很难。

他还提到一个外溢的后果：我们在加重别人的负担。GitHub 上的提交和仓库都多了很多；他认识好几位人，老网站因为 agent 找到了新用途，被直接打来的流量压得吃不消，那些网站根本没准备好迎接这个量。幻灯片上写的受影响对象是 GitHub、npm 和各种第三方网站。

一个朋友的故事

他讲了一个朋友的例子。这位朋友有一个开源项目，已经完全自动化了：issue 进来，有 agent 自动审查、提交、回复。这看起来像是解法，把人拿掉就能放大规模。

结果这位朋友后来自己把它关了。原因是，他对这个项目不那么在乎了，想把 token 额度留给别的事。

Armin 从这里得出的结论是：即使整个流程都自动了，我们对一个开源项目的注意力依然重要。我们一旦不再用某个东西，就倾向于不再主动照顾它。

### 四、他自己的几个做法

查完数据，他得出三件对他来说最重要的事。

1. 知道什么时候说「方向错了」

他的理由是：agent 是被奖励「完成目标」的，而完成没有完成，很容易判断。这和训练时强化学习环境奖励模型的方式类似。但交出来的东西，是不是我们长期真心满意的，是另一回事。

提交越来越多、软件越来越大，就很容易做出一辆「辛普森汽车」，把所有功能都堆进去（他说的是动画片《辛普森一家》里霍默设计的那辆车）。要让东西真正长在一起，让内部复杂度不爆炸，还是需要人在它工作的时候一起工作。

他把这叫作「真本事」对「agent 本事」。有经验的软件工程师和没有经验的人，用同一个 agent，结果不一样。他最直接的证据来自自己家：他儿子现在在给他们一起做的项目发 pull request，质量差别很明显，因为他儿子不是软件工程师。 两个人用的是同一套提示方式。

他还说了一件让人不舒服的事，不止他一个人讲：在真正要紧的场合，房间里别的人只是回头去问 agent，对系统在干什么、要解决的根本问题是什么，都没有真正的理解，这是很令人沮丧的。

2. 速度要压在自己能理解的范围里：70% 处的 HTML 摘要

他的提交数「冲上天花板」之后，他回头去看自己的会话轨迹，想找一个办法，在会话结束前挂上一个检查点，用一致的方式评估正在发生什么。

具体做法是在 prompt 里要求 agent：在走向验证之前（通常大约在整个会话 70% 的位置），先给他写一份简短的执行摘要，是排好版的 HTML 页面，让他在 agent 收尾的时候能看懂它做了什么。他说，用上新模型之后，读 agent 吐出来的文字，已经没有那么痛苦了。

这是他平衡的办法：他承认，很多情况下他已经不再读代码了。 摘要是他保住理解的那根线。

3. 少依赖，但别「野蛮生长」

[/FinanceYF5/article/2121777577903996936/media/2121636615877771266](/FinanceYF5/article/2121777577903996936/media/2121636615877771266)

他的第三点：自己造有时对生态不好；Wildwuchs 伤害互操作；开放协议和文件格式有用；但协作是人最慢的环节。来源：AIE CODE 2026 直播

他是「少用依赖、多自己写」的坚定信徒，所以他喜欢 agent 带来的这一面。但他用了一个德语词，Wildwuchs，意思是不受控的生长。

他举的例子是最近流传的一篇博客：有人构造了一个 TAR 压缩包，不同的 TAR 实现读出来的内容不一样。他由此说，我们要合作，就要标准、规范、通用的文件格式。现在人人都能让 agent 实现任何格式，但实现之间会出现差异；真正难的，从来不是技术，是人怎么就「文件里该有什么、该怎么实现、该怎么解读」达成一致，因为同一份规范可以有多种解读。他描绘的一幅图景是：将来每个人都有自己的 Photoshop 克隆，却发不了文件给彼此，因为已经分叉得太远。

他是做开源出身的，所以他特别说：他看到现在开源项目里真正的人和人协作越来越少，大量项目的 fork 多得数不清，因为 fork 比向上游提交改动容易。他的态度是：有时候要抵制「让 agent 把问题解了」的诱惑，退一步，想想这是不是该和别人一起解决的问题。

多出来的力气放在哪

这一块他说得很快，只讲方向：他看到最近经过验证的软件大量涌现，虽然他承认这条技术栈还没成熟、本身就很难，但值得推。他也很高兴看到很多人想做在根本上更快、更省内存的软件，他多年来对内存被占去做不值得的事很不满，现在有一股趋势是用原生语言重做，而不是再套一个 Electron 外壳。他还喜欢 Rust 和内存安全软件的趋势：好模型在找安全漏洞，这给了内存安全一个强理由，也让以前不会选这门语言的人试了起来，因为它的好处现在可以「几乎白送」。

### 五、他对 harness 的三个期待：持久化、code mode、分类模型

最后一段他说得很谨慎：不是「我们走的路是什么」，而是让大家看看，把任务拉得更长之后，挑战在哪里。

1. 持久的 agent：挂起、恢复

[/FinanceYF5/article/2121777577903996936/media/2121636593471799296](/FinanceYF5/article/2121777577903996936/media/2121636593471799296)

Durability：运行比进程和人的注意力更长；人要几个小时才回答，所以等待必须持久；要聪明地调度推理和算力。来源：AIE CODE 2026 直播

他的出发点是：两分钟的任务，你愿意盯着，出错了、中途停了，手动重启、让它继续就行，过去很长时间大家都在这种环境里工作。但如果有 agent 在一夜之间处理成千上万个 issue，就希望它能自己重启。所以他们相信「durable agents」：由 agent 创造持久的工作流，自己编排自己，可以启动、停止、挂起、恢复。

这不只是因为任务变长，还因为现在有很多低效。大家的算力和推理成本都受限，如果按原价付 token，flex 调度有相当大的折扣；代价是有时候好几分钟没有 token 进来。这时候，就应该把 agent 挂起，连沙箱一起挂起，别让同样昂贵的其他资源空转。

2. code mode：Bash 之外再给一门 JavaScript

[/FinanceYF5/article/2121777577903996936/media/2121636738334674944](/FinanceYF5/article/2121777577903996936/media/2121636738334674944)

Codemode：Bash 编排程序而不是 harness 自己的工具；循环和并发不经过上下文；在 harness 一侧运行，状态留在记录里。来源：AIE CODE 2026 直播

Pi 刚出来的时候，设计动机是「Bash 就是你要运行的一切」，他说他们现在大体上还这么相信。但他也看到，现在出现了编排子 agent 的需求，也出现了用非 LLM 的模型（决策模型、分类模型）的需求，这时候就得把工作流组合起来。

做法最早来自 Cloudflare 的人：不要把成千上万个工具塞进上下文，而是在 Bash 之外，再给 agent 一门 JavaScript，让它本来要做的所有工具调用都通过 JavaScript 来发，这样它能编排得更好。他说这个想法从一个新鲜玩意，变成了「令人震惊地有用」。Codex 里已经有，Pi 里也能这么做。

结果是 harness 可以编排规模很大的一批工具调用，而不用经过低效的上下文。他也说，这确实需要重新想一下以前的做法。

3. 分类模型：每个 if 都交给 Jev

[/FinanceYF5/article/2121777577903996936/media/2121636762649067520](/FinanceYF5/article/2121777577903996936/media/2121636762649067520)

分类模型（Jev、Clef 等）：成批处理模糊的人类任务；问问题，返回选项和分数，不返回长文；在 codemode 和循环里调用，不经过上下文。来源：AIE CODE 2026 直播

有了 code mode，就可以用 Jev 这类分类、决策模型。他说这是另一件改变他对「技术能推多远」看法的事，原因有两个：用它们不会因为没有活跃的 KV cache 而被罚；而且它们又便宜又快，以前太贵或太慢的问题，现在可以让一个决策模型来做。

他给的用法是：harness 用 code mode 现场生成一段小工作流，工作流里的决策点，每一个 if 条件都交给 Jev 判断。他的例子是要处理 3,000 条进来的客服请求，每一步要判断是交给 agent 去处理、还是要向客户要更多反馈。让 agent 现场生成这样一个工作流，然后过一遍几千条，在编码 agent 里「眨眼间」就跑完了，以前要花几个小时。

### 他留下的那句话

收尾他说：既然现在什么都能造了，也许我们不该什么都造。 但我们应该推向更有趣、更有野心的软件。

回到那两组数。120–190 条 prompt，10–15 个仓库，是他一年的会话里最稳定的两个数字，也是工坊和工厂的分界：工厂的产量可以无限涨，工坊里能被好好照看的东西，取决于一个人的注意力。他的做法不是把注意力扩大，而是让自己手里的东西，每一件都是自己能理解、愿意回来的。
