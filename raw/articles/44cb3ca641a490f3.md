Should you rely on public benchmark scores when choosing a model? [@VikParuchuri](/VikParuchuri) argues "no" in this talk.

To illustrate this, he shows specific problems found in popular OCR benchmarks:

ParseBench:

• A test expects 310 gigawatts of solar-panel capacity when the correct value is 303.  Additionally, 73% of its chart tests ask for values that aren't printed on the chart. ([4:51](/HamelHusain/status/2117384307593646230?t=291))

• A test requires "Parish Priest:" to be bold even though those words aren't bold in the source document. ([15:33](/HamelHusain/status/2117384307593646230?t=933))

• The scorer fails to recognize heading tags placed on separate lines. ([16:15](/HamelHusain/status/2117384307593646230?t=975))

• dots.mocr ranks last among six models even though it beats the first-ranked model on content and tables.  This is an example of how overall benchmark score can hide important differences in model capabilities. ([14:48](/HamelHusain/status/2117384307593646230?t=888))

olmOCR-bench:

• A model correctly preserves a line break in a document and gets penalized for it. ([10:30](/HamelHusain/status/2117384307593646230?t=630))

• A test expects "Republican Party" when a document says "Republican party". Copying the capitalization correctly makes the model fail. ([10:49](/HamelHusain/status/2117384307593646230?t=649))

• A 700-line postprocessor that rewrites model output adds 1 to 2 points, more than many gaps between models. ([12:12](/HamelHusain/status/2117384307593646230?t=732))

OmniDocBench:

• This benchmark uses edit distance, which penalizes a correct table written in HTML more heavily than a wrong number in Markdown. So the format matters more than the answer! ([6:58](/HamelHusain/status/2117384307593646230?t=418))

This is just the tip of the iceberg, the video contains more examples.
